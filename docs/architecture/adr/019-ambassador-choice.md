# ADR-019: Выбор Ambassador Pattern для внешних интеграций

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

Система OMS взаимодействует с несколькими внешними сервисами:
- **Платёжный шлюз** (Payment Gateway) — обработка платежей, возвраты.
- **Сервис уведомлений** (Notification Service) — отправка email, SMS, push-уведомлений.
- **Сервис инвентаризации** (Inventory Service) — проверка и резервирование товаров.
- **Внешние API** (например, доставка, трекинг).

Эти интеграции требуют единообразного подхода к:
- **Аутентификации** (токены, API-ключи).
- **Логированию** (входящие/исходящие запросы).
- **Метрикам** (количество вызовов, ошибки, задержки).
- **Политикам повторных попыток** (Retry) и защите от сбоев (Circuit Breaker).
- **Таймаутам** и лимитам.
- **Кэшированию** ответов для снижения нагрузки.

Без единого подхода каждый сервис будет реализовывать эту логику по-своему, что приведёт к дублированию кода, ошибкам и сложности поддержки.

---

## Решение

Внедряем паттерн **Ambassador** как **прокси-сервис (sidecar или отдельный компонент)** для всех внешних вызовов.
