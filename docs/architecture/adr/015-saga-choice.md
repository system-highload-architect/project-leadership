# ADR-015: Выбор стратегии Saga для распределённых транзакций

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

В системе OMS ключевой бизнес-процесс — создание заказа. Он требует согласованных действий в нескольких модулях/сервисах:
1. **Order Service** — создание заказа (статус NEW).
2. **Payment Service** — списание средств (через внешний платёжный шлюз).
3. **Inventory Service** — резервирование товаров.
4. **Notification Service** — отправка подтверждения клиенту.

Эти шаги должны быть выполнены **атомарно** с точки зрения бизнеса: либо все успешно, либо должен произойти откат (компенсация) — например, отмена заказа, возврат платежа, освобождение товаров.

Традиционный подход — **двухфазный коммит (2PC)** — не подходит для распределённых систем (блокировки, низкая масштабируемость, проблемы с доступностью).

Необходимо выбрать подход для управления распределёнными транзакциями.

---

## Решение

Выбран подход **Saga Orchestration** (с центральным координатором).

**Оркестратор** (Saga Coordinator) — отдельный компонент (или модуль внутри Order Service), который управляет последовательностью шагов и компенсирующими действиями при ошибках.

**Схема саги для создания заказа:**

| Шаг | Действие | Компенсация |
|-----|----------|-------------|
| 1 | Order Service: создать заказ (NEW) | Order Service: отменить заказ (CANCELLED) |
| 2 | Payment Service: списать средства | Payment Service: возврат средств |
| 3 | Inventory Service: зарезервировать товары | Inventory Service: освободить резерв |
| 4 | Notification Service: отправить подтверждение | (опционально) отправить уведомление об отмене |

**Реализация:**
- Оркестратор — это **stateful** компонент, который сохраняет состояние саги (в БД или в памяти с репликацией).
- Каждый шаг — это вызов gRPC/REST к соответствующему сервису.
- При ошибке оркестратор запускает компенсацию в **обратном порядке**.
- Все операции должны быть **идемпотентными**.
- Для восстановления после сбоев оркестратор сохраняет состояние и может быть перезапущен.

**Инструменты:**
- Используем **Temporal** или **Camunda** как готовый оркестратор (или пишем свой лёгкий координатор на Go с сохранением состояния в PostgreSQL).
- Для простоты на старте реализуем собственный координатор с использованием паттерна **Saga State Machine**.

---

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Saga Choreography** | Децентрализованность, слабая связанность, нет единой точки отказа | Сложность отладки, мониторинга, риск «бесконечных циклов» событий | Оркестрация даёт лучший контроль и наблюдаемость на старте |
| **Двухфазный коммит (2PC)** | Строгая атомарность, ACID | Блокировки, низкая доступность, не масштабируется | Неприемлемо для распределённых микросервисов |
| **TCC (Try-Confirm-Cancel)** | Подходит для ресурсов с резервированием | Сложность реализации, требует поддержки со стороны сервисов | Избыточен для OMS, Saga проще |
| **Вручную (без координации)** | Простота | Нет гарантий согласованности | Неприемлемо для бизнес-критичных операций |

## Последствия

### Положительные
- ✅ Централизованное управление — лёгкий мониторинг и отладка.
- ✅ Чёткая последовательность шагов, явные точки компенсации.
- ✅ Возможность использования готовых решений (Temporal, Camunda).
- ✅ Масштабируемость — координатор может быть кластеризован.

### Отрицательные
- ❌ Единая точка отказа (координатор) — требует отказоустойчивости.
- ❌ Усложнение архитектуры (появление нового компонента).
- ❌ Увеличение времени выполнения (последовательные вызовы).

### Компромиссы
- Координатор проектируется как **stateless** с сохранением состояния во внешнем хранилище (PostgreSQL) для возможности восстановления.
- Для критических операций (платежи) используем **идемпотентные ключи** (например, `idempotency_key`), чтобы избежать дублирования.
- Внедряем **мониторинг** саг (метрики успеха/ошибок, время выполнения) для анализа производительности.
