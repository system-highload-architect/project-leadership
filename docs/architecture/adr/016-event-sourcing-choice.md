# ADR-016: Выбор Event Sourcing для Order Service

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

Система OMS использует событийно-ориентированную архитектуру (ADR-002) и CQRS (ADR-017). В рамках этих подходов возникает вопрос: **хранить ли события как источник истины (Event Sourcing)** или использовать традиционное хранение текущего состояния (CRUD) с публикацией событий.

**Преимущества Event Sourcing:**
- Полный аудит всех изменений.
- Возможность восстановления состояния на любой момент времени.
- Естественная интеграция с EDA (события уже есть).
- Легкость построения проекций (read models) для CQRS.

**Недостатки Event Sourcing:**
- Сложность реализации (event store, воспроизведение событий).
- Большие объёмы данных (события накапливаются).
- Eventual consistency (задержки между записью и чтением через проекции).
- Требуется идемпотентность и версионирование событий.

В OMS ключевым агрегатом является **Order** (заказ). Его жизненный цикл включает несколько состояний (NEW, PAID, SHIPPED, DELIVERED, CANCELLED) и множество событий (создан, оплачен, отгружен, доставлен, отменён). Аудит изменений заказа критичен для бизнеса (финансовые операции, споры с клиентами).

---

## Решение

**Event Sourcing внедряется только для Order Service** (агрегат Order). Остальные сервисы (Payment, Inventory, Notification) используют традиционное хранение текущего состояния (CRUD) с публикацией событий.

**Обоснование:**

- **Аудит:** Заказы — это финансовые документы. Необходимо знать, кто, когда и почему изменил заказ.
- **Восстановление:** Возможность восстановить состояние заказа на любой момент времени (например, для расследования инцидентов).
- **CQRS:** Event Sourcing идеально сочетается с CQRS — проекции для чтения строятся из событий.
- **Ограниченный объём:** Количество заказов растёт, но не экспоненциально, и события для заказов не слишком велики (несколько десятков событий на заказ).
- **Изоляция сложности:** Только один сервис (Order Service) использует Event Sourcing, что упрощает поддержку и не усложняет остальные сервисы.

**Техническая реализация:**
- Event Store: **PostgreSQL** (таблица `order_events` с полями: `order_id`, `event_type`, `event_data` (JSONB), `created_at`).
- Восстановление агрегата: при загрузке заказа читаем все события и применяем их к агрегату (в памяти или с кэшированием снапшотов).
- Снапшоты: периодически сохраняем текущее состояние заказа, чтобы не воспроизводить все события каждый раз (например, каждые 10 событий).
- Публикация событий: после сохранения события публикуем его в Kafka для других сервисов (проекции, уведомления).

---

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Только CRUD + события** | Проще, меньше данных, быстрее чтение | Нет полного аудита, нельзя восстановить состояние на любой момент | Аудит заказов критичен для бизнеса |
| **Event Sourcing для всех сервисов** | Единообразие, полный аудит для всех сущностей | Сложность для всех сервисов, избыточно для простых сущностей | Только Order требует аудита |
| **Event Sourcing через Kafka (log)** | Хранение событий в Kafka, replay через Kafka Streams | Сложность управления топиками, retention, консьюмерами | Избыточно для OMS, PostgreSQL проще |

## Последствия

### Положительные
- ✅ Полный аудит заказов (кто, когда, что изменил).
- ✅ Возможность восстановить состояние заказа на любой момент.
- ✅ Естественная интеграция с CQRS (проекции строятся из событий).
- ✅ Единый источник истины (события) для Order Service.
- ✅ Лёгкость добавления новых проекций (например, для аналитики).

### Отрицательные
- ❌ Усложнение Order Service (дополнительная логика работы с событиями).
- ❌ Хранение большого количества событий (может потребоваться архивация).
- ❌ Eventual consistency между записью и чтением (проекции обновляются асинхронно).
- ❌ Необходимость версионирования событий (при изменении структуры).

### Компромиссы
- Внедряем **снапшоты** для ускорения загрузки агрегатов.
- Используем **PostgreSQL** как Event Store (простота, знакомый инструмент).
- Внедряем **мониторинг** размера таблицы событий и задержек проекций.
