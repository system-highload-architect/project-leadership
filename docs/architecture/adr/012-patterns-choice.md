# ADR-012: Выбор архитектурных паттернов

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

Для реализации Order Management System (OMS) необходимо выбрать набор архитектурных паттернов, которые обеспечат:
- **Слабость связанности** модулей.
- **Тестируемость** и поддерживаемость.
- **Масштабируемость** и эволюционность.
- **Надёжность** при интеграциях с внешними системами.

Паттерны должны покрывать:
- Организацию кода внутри модулей.
- Коммуникацию между модулями.
- Работу с данными и событиями.
- Устойчивость к сбоям и распределённые транзакции.

---

## Решение

Выбраны следующие архитектурные паттерны:

### 1. **Clean Architecture** — для организации кода внутри каждого модуля/сервиса
- **Слои:** Domain → Use Cases → Delivery → Infrastructure.
- **Направление зависимостей:** Внутрь (внешние слои зависят от внутренних).
- **Использование:** Все бизнес-модули (Order, Payment, Notification, Product).

### 2. **Event-Driven Architecture (EDA)** — для коммуникации между модулями
- **Брокер:** Apache Kafka.
- **События:** OrderCreated, PaymentProcessed, OrderShipped, OrderCancelled и т.д.
- **Использование:** Слабая связанность, асинхронность, аудит.

### 3. **CQRS (Command Query Responsibility Segregation)** — для разделения команд и запросов (опционально, для read-интенсивных сценариев)
- **Команды:** Изменяют состояние (CreateOrder, CancelOrder).
- **Запросы:** Читают данные (GetOrder, ListOrders).
- **Использование:** Для сложных аналитических запросов (отчёты, дашборды).

### 4. **Saga (Choreography)** — для распределённых транзакций
- **Управление:** Хореография (без центрального координатора).
- **Использование:** При создании заказа (Order → Payment → Notification → Inventory).

### 5. **Circuit Breaker** — для защиты от каскадных сбоев при интеграциях
- **Использование:** При вызове внешних сервисов (Payment Gateway, Notification Service).

### 6. **Retry with Backoff** — для устойчивости к временным сбоям
- **Использование:** При работе с сетью, БД, Kafka.

### 7. **Sidecar** — для выноса сквозной функциональности
- **Использование:** Логирование, метрики, трассировка (OpenTelemetry), Health Checks.

### 8. **Strangler Pattern** — для постепенной замены устаревших модулей
- **Использование:** При миграции от монолита к микросервисам (если потребуется).

---

## Альтернативы

| Паттерн | Альтернатива | Почему выбрано |
|---------|--------------|----------------|
| Clean Architecture | Layered (n-tier) | Clean даёт лучшую тестируемость и гибкость |
| EDA | Синхронные REST/gRPC вызовы | EDA даёт слабую связанность и аудит |
| CQRS | CRUD | CQRS необходим для сложных read-моделей (отчёты) |
| Saga | Двухфазный коммит (2PC) | 2PC не масштабируется, Saga — стандарт для микросервисов |
| Circuit Breaker | Без защиты | Circuit Breaker обязателен для внешних интеграций |
| Retry | Без повторных попыток | Повышает устойчивость системы |
| Sidecar | Встраивание логирования в код | Sidecar упрощает обновление сквозных функций |
| Strangler | Полная перезапись системы | Strangler снижает риски миграции |

---

## Последствия

### Положительные
- ✅ Слабая связанность, лёгкость изменения и расширения.
- ✅ Высокая тестируемость (Clean Architecture, CQRS).
- ✅ Надёжность (Circuit Breaker, Retry, Saga).
- ✅ Единый стиль кода во всех модулях.

### Отрицательные
- ❌ Увеличение сложности (больше паттернов → больше кода и конфигурации).
- ❌ Требуется обучение команды работе с EDA, CQRS, Saga.

### Компромиссы
- CQRS внедряем только для read-интенсивных сценариев (не для всех модулей).
- Saga используем только для критических распределённых транзакций.
- Circuit Breaker и Retry реализуем через `go-resiliency` или аналоги.
