# ADR-006: Выбор брокера сообщений

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст
Система использует событийно-ориентированную архитектуру. Необходим брокер для публикации и доставки событий (заказы, платежи, уведомления). Требования:
- Высокая пропускная способность.
- Гарантии доставки (at-least-once/ exactly-once).
- Долговременное хранение событий (replay).
- Поддержка масштабирования.

Рассматривались Kafka, RabbitMQ, NATS.

## Решение
Выбран **Apache Kafka** как основной брокер сообщений.

**Обоснование:**
- Высокая пропускная способность и низкая задержка.
- Сохранение событий на диске — возможность replay.
- Поддержка партиционирования, групп потребителей.
- Интеграция с Debezium для CDC из PostgreSQL.

## Альтернативы
- **RabbitMQ**: сложнее с replay, меньше пропускная способность, нет долговременного хранения.
- **NATS**: хорош для микросервисов, но слабее с гарантиями доставки и replay.

## Последствия
- ✅ Масштабируемость, replay-событий, надёжность.
- ❌ Операционная сложность (настройка кластера, управление топиками).
- Внедряем мониторинг (Prometheus + Grafana) для Kafka.
