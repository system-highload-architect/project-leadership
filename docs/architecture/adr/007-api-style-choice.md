# ADR-007: Выбор стиля API (REST vs gRPC)

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

Система Order Management System (OMS) предоставляет API для внешних клиентов (веб-приложение, мобильные приложения, сторонние интеграции) и для внутреннего взаимодействия между сервисами. Необходимо выбрать основной стиль построения API.

Требования к API:
- Высокая производительность (низкая задержка, высокая пропускная способность).
- Чёткая контрактная модель (версионирование, обратная совместимость).
- Удобство для внешних клиентов (браузеры, мобильные устройства).
- Возможность стриминга данных.
- Простота разработки и документирования.

Рассматривались:
1. **RESTful API (HTTP/1.1 + JSON)**
2. **gRPC (HTTP/2 + Protobuf)**
3. **GraphQL** (для гибких запросов)

---

## Решение

Принят **гибридный подход**:

- **Для внешних API (публичных)** — **RESTful API** (OpenAPI 3.0, JSON).
- **Для внутренних сервисов** — **gRPC** (Protobuf).

**Обоснование:**

**REST для внешних API:**
- Простота и привычность для фронтенда и мобильных разработчиков.
- Отличная поддержка браузерами, кэширование (HTTP-кэш, CDN).
- Легко документировать через OpenAPI/Swagger.
- Гибкость версионирования через URL (`/v1/orders`).

**gRPC для внутренних сервисов:**
- Высокая производительность (бинарный протокол, мультиплексирование).
- Строгие контракты (Protobuf) — гарантия совместимости.
- Поддержка стриминга (например, поток событий).
- Эффективнее REST для микросервисной коммуникации.

---

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
|--------------|-------|--------|-------------------|
| **Только REST** | Простота, универсальность | Низкая производительность для внутренних вызовов, нет стриминга | Недостаточно эффективен для микросервисов |
| **Только gRPC** | Высокая производительность, стриминг | Сложность для внешних клиентов (браузеры, мобильные), нет HTTP-кэширования | Внешние клиенты будут испытывать трудности |
| **GraphQL** | Гибкость запросов (клиент выбирает поля) | Сложность реализации, кэширование, перегрузка БД | Избыточен для OMS, добавляет сложность без явной выгоды |

---

## Последствия

### Положительные
- ✅ Внешние клиенты получают простой и понятный REST API.
- ✅ Внутренние сервисы общаются быстро и надёжно через gRPC.
- ✅ Чёткие контракты для каждого стиля.
- ✅ Возможность миграции части внешних запросов на GraphQL в будущем (если потребуется).

### Отрицательные
- ❌ Поддержка двух стилей API — дополнительная сложность разработки и документирования.
- ❌ Требуется управление двумя наборами контрактов (OpenAPI + Protobuf).
- ❌ Необходимость в шлюзе для трансляции gRPC в REST (если внешние клиенты захотят использовать gRPC).

### Компромиссы
- Используем **gRPC Gateway** для автоматической генерации REST-эндпоинтов из Protobuf (упрощает поддержку).
- Документируем оба API через OpenAPI и Protobuf-комментарии.
- Внедряем единую систему аутентификации (JWT), общую для обоих стилей.
