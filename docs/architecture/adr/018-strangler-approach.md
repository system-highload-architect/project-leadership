# ADR-018: Выбор Strangler Pattern для эволюционной миграции

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

Система OMS начинается как **модульный монолит** (ADR-001). Однако в будущем, по мере роста команды и нагрузки, может потребоваться переход к **микросервисной архитектуре** (ADR-003). Такой переход — это сложный и рискованный процесс, особенно если пытаться сделать его «за один раз» (big bang).

Необходимо выбрать стратегию миграции, которая позволит:
- Постепенно выносить функциональность из монолита в отдельные сервисы.
- Минимизировать риски и простои.
- Сохранить работоспособность системы на всех этапах.
- Обеспечить возможность отката на любом этапе.

---

## Решение

Принята стратегия **Strangler Pattern** (паттерн «Душитель») для эволюционной миграции монолита к микросервисам.

**Этапы миграции:**

1. **Создание API Gateway** — единая точка входа для всех клиентов, которая будет маршрутизировать запросы либо к монолиту, либо к новым сервисам.

2. **Выделение первого сервиса** (например, Payment Service) — реализуем его как отдельный микросервис, а API Gateway направляет запросы к нему. Монолит продолжает работать для остальной функциональности.

3. **Переключение трафика** — постепенно увеличиваем процент запросов, направляемых на новый сервис (canary release), мониторим ошибки и производительность.

4. **Выделение следующих сервисов** — повторяем процесс для Inventory, Notification, User и т.д.

5. **Удаление функциональности из монолита** — когда новый сервис полностью заменит старую функциональность, удаляем соответствующий код из монолита.

6. **Полный переход** — монолит становится либо «ядром», либо полностью заменяется набором микросервисов.

**Инструменты:**
- **API Gateway:** Envoy или KrakenD (лёгкий, быстрый, поддерживает маршрутизацию по заголовкам/путям).
- **Feature Flags:** Используем LaunchDarkly или самодельную реализацию для гибкого переключения трафика.
- **Мониторинг:** Prometheus + Grafana для отслеживания ошибок и задержек при переключении трафика.

---

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Big Bang (полная перезапись)** | Единообразие, отсутствие промежуточных состояний | Высокий риск, длительный простой, сложность тестирования | Слишком рискованно для production |
| **Strangler Pattern** | Безопасная миграция, возможность отката, постоянная работоспособность | Требует дополнительной инфраструктуры (Gateway, Feature Flags), затянутый процесс | Выбран, так как минимизирует риски |
| **Parallel Run (запуск двух систем параллельно)** | Возможность сравнения результатов | Удвоение нагрузки и затрат на инфраструктуру | Избыточно для OMS |

## Последствия

### Положительные
- ✅ Безопасная миграция без простоев.
- ✅ Возможность отката на любом этапе.
- ✅ Постепенное обучение команды микросервисам.
- ✅ Гибкость — можно переключать трафик по пользователям/фичам.

### Отрицательные
- ❌ Усложнение архитектуры (дополнительный слой — API Gateway).
- ❌ Длительность процесса (миграция может занять 6–12 месяцев).
- ❌ Необходимость поддерживать обратную совместимость между старой и новой версиями API.

### Компромиссы
- Начинаем миграцию с **самого простого и изолированного модуля** (например, Notification Service), чтобы наработать опыт.
- Используем **Feature Flags** для постепенного переключения пользователей.
- Внедряем **сквозное тестирование** (e2e) для проверки работы Gateway и нового сервиса.
