# ADR-020: Выбор Sidecar Pattern для сквозной функциональности

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

В системе OMS каждый сервис должен предоставлять сквозную функциональность:
- **Логирование** (структурированное, с TraceID).
- **Метрики** (количество запросов, ошибки, задержки).
- **Трассировка** (OpenTelemetry, распределённая трассировка).
- **Health Checks** (готовность, живость).
- **Управление конфигурацией** (горячая перезагрузка).
- **Аутентификация и авторизация** (JWT проверка).

Без единого подхода каждый сервис будет реализовывать эту логику по-своему, что приведёт к дублированию, ошибкам и сложности поддержки. Также это усложнит обновление сквозных функций (например, добавление нового поля в логи).

---

## Решение

Внедряем паттерн **Sidecar** — отдельный контейнер (процесс), который запускается рядом с каждым экземпляром сервиса и предоставляет сквозную функциональность.
