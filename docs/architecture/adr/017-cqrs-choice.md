# ADR-017: Выбор CQRS для Order Service

**Статус:** Принято  
**Дата:** 2026-07-25  
**Автор:** Tech Lead

---

## Контекст

В OMS есть несколько сценариев с разными паттернами нагрузки:
- **Команды:** Создание заказа, отмена заказа, изменение статуса, обновление платёжной информации. Эти операции изменяют состояние системы, должны быть согласованными и транзакционными.
- **Запросы:** Получение заказа по ID, список заказов клиента, поиск заказов по дате/статусу, аналитические отчёты (количество заказов за период, сумма продаж и т.д.). Запросы могут быть сложными, включать фильтрацию, сортировку, агрегацию, пагинацию.

Использование одной модели данных (CRUD) для обоих типов операций приводит к:
- Конфликту между оптимизацией записи (нормализованная схема) и чтения (денормализованная, с индексами).
- Риску блокировок при одновременной записи и чтении (особенно в аналитических запросах).
- Сложности масштабирования: нельзя независимо масштабировать чтение и запись.

Необходимо выбрать подход для разделения команд и запросов.

---

## Решение

Внедряем **CQRS (Command Query Responsibility Segregation)** для Order Service.  
**Команды** используют текущее состояние (агрегаты) и сохраняются в Event Store (ADR-016).  
**Запросы** используют отдельные проекции (read models), построенные из событий, оптимизированные для чтения.
