# Модель данных

**Версия:** 1.0  
**Дата:** 2026-07-26  
**Статус:** Черновик

---

## 1. Введение

Данный документ описывает **модель данных** E‑Commerce платформы, которая реализована в PostgreSQL 15+ и полностью соответствует архитектурным решениям, зафиксированным в ADR.

**Ключевые принципы модели:**
- **Разделение ответственности (CQRS)** — write-модель (нормализованная) и read-модели (денормализованные проекции) живут в разных схемах (опционально — в разных БД).
- **Event Sourcing** — для Order Service используется таблица `order_events` как источник истины.
- **Saga** — таблица `saga_state` хранит состояние распределённых транзакций (оркестратор).
- **Событийная интеграция** — изменения в таблицах (`users`, `orders`, `payments`) через Debezium публикуются в Kafka.
- **Гибкость** — JSONB-поля (`external_data` в платежах, `instruction` в саге) позволяют адаптироваться к изменениям без миграций схемы.

---

## 2. Связь с архитектурными паттернами

| Паттерн | Как отражён в модели данных |
|---------|-----------------------------|
| **Модульный монолит** | Единая БД, но схемы логически разделены по модулям (`orders`, `payments`, `products`, `users`). |
| **CQRS** | Write-модель — нормализованные таблицы (`orders`, `order_items`). Read-модели — денормализованные проекции (например, `orders_read` или отдельная БД для аналитики). |
| **Event Sourcing** | Таблица `order_events` хранит все события (OrderCreated, OrderPaid, OrderShipped, OrderCancelled). Агрегат Order восстанавливается из них. |
| **Saga** | Таблица `saga_state` хранит состояние оркестратора (инструкция, результаты шагов). |
| **EDA** | CDC (Debezium) публикует изменения в Kafka для всех таблиц. |
| **Абстрактные инструкции** | JSONB-поле `instruction` в `saga_state` позволяет передавать сложные бизнес-инструкции без изменения схемы. |

## 3. Основные сущности

### 3.1 Пользователи (`users`)
Хранит информацию о клиентах, менеджерах и администраторах.  
**Связи:** один пользователь → одна корзина (`carts`), много заказов (`orders`).

### 3.2 Товары (`products`)
Каталог товаров с остатками (`stock`).  
**Связи:** участвует в `cart_items` и `order_items`.

### 3.3 Корзина (`carts`, `cart_items`)
Хранит временные позиции до оформления заказа.  
**Связи:** одна корзина → много позиций (`cart_items`). Позиция ссылается на `products`.

### 3.4 Заказы (`orders`, `order_items`)
Основная бизнес-сущность. Статусы: `NEW`, `PAID`, `SHIPPED`, `DELIVERED`, `CANCELLED`.  
**Связи:** один заказ → много позиций (`order_items`). Позиция сохраняет снэпшот названия товара и цены на момент заказа.

**Важно:** для заказов используется **Event Sourcing** — все изменения фиксируются в `order_events`.

### 3.5 Платежи (`payments`)
Связаны с заказами. Статусы: `PENDING`, `SUCCESS`, `FAILED`, `REFUNDED`.  
JSONB-поле `external_data` хранит ответы платёжного шлюза для отладки.

### 3.6 События (`order_events`)
Таблица для Event Sourcing. Содержит все события, относящиеся к конкретному заказу (`aggregate_id`).  
Поле `event_data` — JSONB с полным контекстом события.  
**Используется** для восстановления агрегата и построения проекций.

### 3.7 Состояние саги (`saga_state`)
Хранит состояние распределённых транзакций.  
Поле `instruction` — JSONB с абстрактной инструкцией (шаги, зависимости).  
Поле `step_results` — JSONB с результатами выполнения шагов.

## 5. Миграции

Для управления схемой используется `golang-migrate` (или `migrate`).  
Файлы миграций хранятся в `migrations/` (отдельная папка в проекте) и применяются через `make migrate-up`.

**Пример команды:**
```bash
make migrate-up   # Применить все миграции
make migrate-down # Откатить последнюю миграцию
```

## 6. Индексы и производительность

Для каждой таблицы созданы индексы на часто используемые поля:
- `users.email` — уникальный индекс.
- `orders.user_id`, `orders.status`, `orders.created_at`.
- `order_items.order_id`, `order_items.product_id`.
- `payments.order_id`, `payments.status`, `payments.transaction_id`.
- `order_events.aggregate_id`, `order_events.created_at`.
- `saga_state.saga_type`, `saga_state.status`.

Эти индексы обеспечивают быстрый поиск, фильтрацию и пагинацию.

## 7. Связь с API-контрактами

Модель данных полностью соответствует API-контрактам:
- REST API (OpenAPI) — сущности `Product`, `Order`, `Payment`, `User`, `Cart` маппятся на таблицы.
- gRPC (Protobuf) — аналогично маппятся на те же таблицы.

---

## 8. Эволюция модели

Модель данных будет эволюционировать вместе с системой:
- Добавление новых полей через миграции.
- Переход на партиционирование (по `created_at`) при росте данных.
- Внедрение шардирования (Citus) при необходимости.
- Вынос read-моделей в отдельную БД (ClickHouse) для аналитики.
