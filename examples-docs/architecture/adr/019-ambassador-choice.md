
**Реализация Ambassador:**

Ambassador может быть реализован двумя способами:
1. **Как отдельный сервис** (кластер прокси) для всех вызовов из системы.
2. **Как Sidecar** (в каждом Pod'е) для максимальной изоляции.

На старте мы выбираем **отдельный Ambassador-сервис** (кластер), так как это проще в управлении и мониторинге. Позже, при переходе на микросервисы, можно перейти на Sidecar-модель (как часть Service Mesh).

**Функциональность Ambassador:**
- **Retry with Backoff** (экспоненциальная задержка, настраивается под каждый сервис).
- **Circuit Breaker** (защита от каскадных сбоев, настраиваемые пороги).
- **Таймауты** (индивидуально для каждого внешнего сервиса).
- **Кэширование GET-запросов** (TTL настраивается, например, для каталога товаров).
- **Аутентификация** (добавляет токены/ключи к запросам, обновляет их при истечении).
- **Логирование** (все запросы/ответы в структурированном формате с TraceID).
- **Метрики** (количество вызовов, ошибки, латентность, HTTP-статусы — в Prometheus).
- **Трансформация** (маппинг ответов внешних сервисов во внутренние DTO).
- **Валидация** (проверка ответов на соответствие контракту).

**Инструменты:**
- **На старте** используем **самописный Ambassador на Go** (как часть инфраструктурного пакета `resiliency`), потому что:
  - Мы контролируем логику и можем быстро её менять.
  - Легче интегрировать с нашим стеком (Go, gRPC, HTTP).
  - Нет зависимости от внешних инструментов (Envoy, KrakenD, которые могут быть избыточны на старте).
- **В перспективе** (при переходе на микросервисы) можем использовать **Envoy** или **KrakenD** как более производительные и функциональные решения.

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Прямой вызов (без Ambassador)** | Простота, минимум инфраструктуры | Дублирование логики в каждом сервисе, сложность изменений | Неприемлемо для масштабирования |
| **Sidecar Pattern** | Ambassador — это частный случай Sidecar | Ambassador может быть общим для нескольких сервисов | Выбираем Ambassador как более гибкий и централизованный вариант на старте |
| **API Gateway** | Централизованное управление внешними вызовами | API Gateway не рассчитан на большое количество вызовов между сервисами (внутренние вызовы) | Ambassador лёгкий и распределённый |
| **Service Mesh** | Istio/Linkerd решают те же задачи | Избыточен для OMS на старте, сложность настройки | Добавим позже при переходе на микросервисы |

## Последствия

### Положительные
- ✅ Единое место для управления внешними интеграциями.
- ✅ Снижение дублирования кода и упрощение поддержки.
- ✅ Лёгкость добавления новых политик (ретраи, кэширование, аутентификация) без изменения сервисов.
- ✅ Единые метрики и логи для всех внешних вызовов.
- ✅ Возможность кэширования на уровне Ambassador (снижение нагрузки на внешние сервисы).
- ✅ Упрощение отладки — все внешние вызовы проходят через одну точку.
- ✅ Быстрое внедрение изменений политик без передеплоя сервисов.

### Отрицательные
- ❌ Дополнительный компонент (ambassador) — увеличивается сложность развёртывания и отладки.
- ❌ Дополнительная задержка (один сетевой hop) — но она минимальна, так как ambassador работает внутри кластера.
- ❌ Требуется управление конфигурацией (для каждого внешнего сервиса свои политики).
- ❌ Ambassador может стать узким местом при высокой нагрузке (необходимо масштабирование).

### Компромиссы
- Ambassador запускается как **отдельный сервис** (кластер), который масштабируется горизонтально при росте нагрузки.
- Конфигурация Ambassador хранится в **ConfigMap** и обновляется без перезапуска сервисов (горячая перезагрузка).
- Внедряем **health-проверки** Ambassador для мониторинга его состояния.
- Для критических внешних сервисов (платёжный шлюз) настраиваем индивидуальные политики (более низкие таймауты, меньше ретраев, более строгий Circuit Breaker).

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Ambassador |
|-------------------|--------------------------|
| **Circuit Breaker** | Реализуется внутри Ambassador. |
| **Retry** | Реализуется внутри Ambassador. |
| **EDA (Kafka)** | Ambassador вызывает внешние API по событиям из Kafka (например, отправка уведомлений). |
| **Saga** | Ambassador используется для вызовов внешних сервисов в рамках Saga (платёжный шлюз). |
| **CQRS** | Ambassador используется для получения данных из внешних систем для read-моделей. |
| **Service Mesh** | Ambassador может быть заменён на Service Mesh (Envoy) при переходе на микросервисы. |
| **Sidecar** | Ambassador может быть реализован как Sidecar в каждом Pod'е. |
