# ADR-002: Выбор событийно-ориентированной архитектуры (EDA)

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Мы строим E‑Commerce платформу, в которой множество сущностей (заказы, платежи, товары, пользователи, уведомления) изменяют свои состояния. Разные части системы должны реагировать на изменения (например, при создании заказа нужно зарезервировать товары, обработать платёж, отправить уведомление).

В будущем мы планируем внедрение:
- **Saga** для распределённых транзакций (платёж + резервирование + уведомление).
- **CQRS** для разделения команд и запросов.
- **Event Sourcing** для аудита заказов.
- **Гибкой бизнес-логики** через абстрактные инструкции (Saga + EDA + CQRS).

Внутри модульного монолита модули должны быть слабо связаны. На старте мы используем внутреннюю шину событий (in‑memory), которая в будущем будет заменена на Kafka без изменения кода модулей.

Перед нами выбор: строить систему на синхронных вызовах (REST/gRPC) или использовать асинхронную событийную модель.

---

## Решение

Мы выбираем **событийно-ориентированную архитектуру (EDA)** как основной способ коммуникации между модулями, а в перспективе — между микросервисами.

Это означает:
1. **Все изменения состояния** публикуются как события (например, `OrderCreated`, `PaymentProcessed`, `OrderShipped`, `OrderCancelled`).
2. **Модули общаются через события**, а не через прямые вызовы.
3. **События публикуются в шину** (на старте — in‑memory, позже — Kafka) и могут быть использованы любым подписчиком.
4. **Каждый модуль** подписывается на события, которые ему интересны, и реагирует на них.
5. **События могут быть сложными контейнерами** — содержать абстрактные бизнес-инструкции для гибкой координации (Saga + EDA + CQRS). Это позволяет описывать бизнес-процессы декларативно, а не императивно.

## Альтернативы

### 1. Синхронная архитектура (REST/gRPC вызовы)
- **Плюсы:** Простота реализации, мгновенный ответ, легче отлаживать.
- **Минусы:** Жёсткая связанность, каскадные отказы, сложность добавления новых потребителей.
- **Почему не выбран:** Не даёт нужной гибкости для будущих интеграций и масштабирования.

### 2. Комбинированный подход (синхронные команды + асинхронные события)
- **Плюсы:** Лучшее из двух миров: команды возвращают результат, события — для уведомлений.
- **Минусы:** Сложность поддержки двух моделей.
- **Почему не выбран:** Мы хотим максимизировать слабую связанность, поэтому предпочитаем события даже для команд (через паттерн «команда как событие» или через абстрактные инструкции).

### 3. Только Event Sourcing (без текущего состояния)
- **Плюсы:** Полный аудит, возможность восстановления на любой момент.
- **Минусы:** Высокая сложность, большие объёмы данных.
- **Почему не выбран:** На старте это избыточно. Мы используем события для коммуникации, но храним текущее состояние в БД (смешанный подход). Event Sourcing будет внедрён позже только для Order Service.

## Последствия

### Положительные
- ✅ **Слабая связанность** — модули не знают друг о друге, только о событиях.
- ✅ **Лёгкость добавления новых функций** — новый подписчик просто подключается к потоку событий.
- ✅ **Асинхронность** — система не блокируется на медленных операциях.
- ✅ **Аудит** — все изменения фиксируются как события (можно отследить историю).
- ✅ **Масштабируемость** — события можно обрабатывать параллельно.
- ✅ **Гибкость бизнес-логики** — через абстрактные инструкции можно менять бизнес-процессы без изменения кода сервисов.

### Отрицательные
- ❌ **Сложность отладки** — распределённые потоки событий сложнее трассировать.
- ❌ **Eventual consistency** — данные могут быть несогласованными в короткие моменты времени.
- ❌ **Дополнительная инфраструктура** — нужен брокер (Kafka) и управление событиями.
- ❌ **Идемпотентность** — обработчики событий должны быть идемпотентными.

### Компромиссы
- Для критических операций (например, создание заказа) мы используем **Saga Orchestration** для гарантии согласованности (см. ADR-015).
- Все события версионируются (например, `OrderCreatedV1`), чтобы обеспечить обратную совместимость.
- Внедряем **трассировку** (OpenTelemetry) для отслеживания цепочек событий.
- На старте используем **внутреннюю шину** (in‑memory), абстрагированную через интерфейс, чтобы позже заменить на Kafka без изменения кода модулей.

## Связь с будущими паттернами

EDA является фундаментом для многих других паттернов:

| Паттерн | Как связан с EDA |
|---------|------------------|
| **Saga** | Реализуется через события (хореография) или через оркестратор, который публикует события (оркестрация) |
| **CQRS** | Команды → события → проекции (read‑модели) |
| **Event Sourcing** | Хранение событий как источника истины |
| **Абстрактные бизнес-инструкции** | События могут содержать инструкции для координации сложных бизнес-процессов, что позволяет гибко управлять логикой без изменения кода |
