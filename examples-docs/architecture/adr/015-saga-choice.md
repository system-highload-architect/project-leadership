# ADR-015: Выбор стратегии Saga для распределённых транзакций

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

В системе E‑Commerce ключевой бизнес-процесс — **создание заказа**. Он требует согласованных действий в нескольких модулях:
1. **Order Service** — создание заказа (статус NEW).
2. **Payment Service** — списание средств (через внешний платёжный шлюз, включая холдирование, подтверждение, возврат при ошибке).
3. **Inventory Service** — резервирование товаров (уменьшение остатков, возврат при отмене).
4. **Notification Service** — отправка подтверждения клиенту (email, SMS, push).

Эти шаги должны быть выполнены **атомарно** с точки зрения бизнеса: либо все успешно, либо должен произойти откат (компенсация) — например, отмена заказа, возврат платежа, освобождение товаров.

Традиционный подход — **двухфазный коммит (2PC)** — не подходит для распределённых систем (блокировки, низкая масштабируемость, проблемы с доступностью).

Необходимо выбрать подход для управления распределёнными транзакциями, который:
- Обеспечивает согласованность данных между модулями.
- Масштабируется и устойчив к сбоям.
- Поддерживает гибкую бизнес-логику (возможность изменения последовательности шагов, добавления новых шагов без переписывания сервисов).
- Интегрируется с EDA и CQRS.
- Позволяет управлять сложными процессами (включая параллельные шаги, условия, компенсации).

---

## Решение

Выбран **гибридный подход к Saga**:

- **Оркестрация (Orchestration)** — для управления общим процессом (создание заказа), где центральный координатор (оркестратор) управляет последовательностью шагов и компенсациями.
- **Хореография (Choreography)** — для внутренних шагов, где сервисы общаются через события (например, уведомления, обновление статусов, логирование).

**Оркестратор** — это отдельный компонент (или модуль внутри Order Service), который:
- Получает команду на выполнение бизнес-процесса (например, `CreateOrderCommand`).
- Формирует **абстрактную инструкцию** (контейнер событий с описанием шагов, зависимостей, условий).
- Отправляет инструкцию в очередь (Kafka) и управляет её выполнением.
- Отслеживает состояние саги (сохраняет в БД для восстановления после сбоев).
- При ошибке запускает компенсацию в обратном порядке.

**Хореография** — для внутренних шагов:
- Сервисы подписываются на события (Kafka) и реагируют на них.
- Например, после успешного платежа публикуется событие `PaymentCompleted`, на которое подписывается Inventory Service для резервирования товаров.
- Это даёт слабую связанность и масштабируемость.

**Абстрактные инструкции** — ключевая особенность:
- Оркестратор не передаёт конкретные команды («сходи в Payment Service, вызови метод ProcessPayment»), а описывает **что нужно сделать** в виде абстрактного набора событий и зависимостей.
- Например: `{ type: "payment", value: "sbp_hold", dependencies: { "reserve": "parallel", "notify": "after" } }`.
- Сервисы сами интерпретируют инструкцию и решают, как её выполнить (на основе своего внутреннего состояния и контракта).
- Это делает бизнес-логику гибкой и эволюционирующей.

## Архитектура Saga (схема)

```
[ Клиент ] → [ API Gateway ] → [ Оркестратор ]
                                    │
                                    ▼
                           [ Создание абстрактной инструкции ]
                                    │
                                    ▼
                           [ Публикация события-инструкции в Kafka ]
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              [ Payment ]     [ Inventory ]    [ Notification ]
                 Service         Service          Service
                    │               │               │
                    └───────────────┴───────────────┘
                                    │
                                    ▼
                           [ События успеха/ошибки в Kafka ]
                                    │
                                    ▼
                           [ Оркестратор обновляет состояние саги ]
                                    │
                                    ▼
                           [ Компенсация при ошибке ]
```

## Реализация Saga (схема состояний)

```go
type SagaState struct {
    ID          string
    Status      string // NEW, IN_PROGRESS, COMPLETED, FAILED, CANCELLED
    Instruction Instruction
    StepResults map[string]StepResult
    CreatedAt   time.Time
    UpdatedAt   time.Time
}

type Instruction struct {
    Type         string                 `json:"type"`          // "create_order", "refund", etc.
    Value        map[string]interface{} `json:"value"`        // абстрактные параметры
    Steps        []Step                 `json:"steps"`         // последовательность/параллельность
    Dependencies map[string]string      `json:"dependencies"`  // зависимости между шагами
}

type Step struct {
    ID          string
    Type        string                 // "payment", "reserve", "notify"
    Value       map[string]interface{}
    Parallel    bool                   // true — параллельно с другими
    Compensate  bool                   // нужно ли компенсировать при ошибке
}
```

## Пример: создание заказа (абстрактная инструкция)

```json
{
  "type": "create_order",
  "value": {
    "customer_id": "123",
    "items": [{"product_id": "p1", "quantity": 2}]
  },
  "steps": [
    {
      "id": "step1",
      "type": "payment",
      "value": {
        "method": "sbp_hold",
        "amount": 1000
      },
      "parallel": false,
      "compensate": true
    },
    {
      "id": "step2",
      "type": "reserve",
      "value": {
        "items": [{"product_id": "p1", "quantity": 2}]
      },
      "parallel": true,
      "compensate": true
    },
    {
      "id": "step3",
      "type": "notify",
      "value": {
        "customer_id": "123",
        "message": "Заказ создан"
      },
      "parallel": false,
      "compensate": false
    }
  ],
  "dependencies": {
    "step1": "step3",
    "step2": "step3"
  }
}
```

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Saga Choreography (только события)** | Децентрализованность, слабая связанность, нет единой точки отказа | Сложность отладки, мониторинга, риск «бесконечных циклов» событий | Оркестрация даёт лучший контроль и наблюдаемость на старте |
| **Saga Orchestration (только оркестратор)** | Централизованное управление, лёгкий мониторинг и отладка, чёткая последовательность | Единая точка отказа (координатор), жёсткая связанность | Гибрид даёт лучшее из обоих миров |
| **Двухфазный коммит (2PC)** | Строгая атомарность, ACID | Блокировки, низкая доступность, не масштабируется | Неприемлемо для распределённых микросервисов |
| **TCC (Try-Confirm-Cancel)** | Подходит для ресурсов с резервированием | Сложность реализации, требует поддержки со стороны сервисов | Избыточен для E‑Commerce, Saga проще |
| **Вручную (без координации)** | Простота | Нет гарантий согласованности | Неприемлемо для бизнес-критичных операций |

## Последствия

### Положительные
- ✅ Централизованное управление — лёгкий мониторинг и отладка (оркестратор).
- ✅ Слабая связанность внутренних шагов (хореография).
- ✅ Гибкость бизнес-логики через абстрактные инструкции.
- ✅ Возможность масштабирования (координатор может быть кластеризован, сервисы горизонтально масштабируются).
- ✅ Интеграция с EDA (Kafka) и CQRS.
- ✅ Чёткая последовательность шагов, явные точки компенсации.

### Отрицательные
- ❌ Единая точка отказа (координатор) — требует отказоустойчивости (репликация, сохранение состояния).
- ❌ Усложнение архитектуры (появление нового компонента — оркестратора).
- ❌ Увеличение времени выполнения (последовательные вызовы, но параллельные шаги ускоряют процесс).
- ❌ Сложность дизайна абстрактных инструкций (требует глубокого понимания предметной области).

### Компромиссы
- Координатор проектируется как **stateless** (состояние сохраняется в PostgreSQL) для возможности восстановления после сбоев.
- Для критических операций (платежи) используем **идемпотентные ключи** (например, `idempotency_key`), чтобы избежать дублирования.
- Внедряем **мониторинг** саг (метрики успеха/ошибок, время выполнения, количество активных саг) для анализа производительности.
- Абстрактные инструкции версионируем (v1, v2) для обратной совместимости.

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Saga |
|-------------------|---------------------|
| **EDA** | Saga использует события для коммуникации (Kafka) |
| **CQRS** | Команды (создание заказа) запускают Saga. Запросы (статус заказа) читаются из проекций. |
| **Event Sourcing** | Saga может сохранять события как источник истины для аудита. |
| **Circuit Breaker / Retry** | При сбое внешнего сервиса (платёжный шлюз) после исчерпания Retry, Saga инициирует компенсацию. |
| **Ambassador** | Ambassador управляет вызовами к внешним сервисам, которые использует Saga. |
| **Sidecar** | Логирование, метрики, трассировка для Saga. |
| **Strangler** | При переходе на микросервисы, Saga остаётся неизменной (оркестратор становится отдельным сервисом). |
| **Абстрактные инструкции** | Центральный элемент Saga — гибкость бизнес-логики. |
