# ADR-017: Выбор CQRS для Order Service

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

В E‑Commerce платформе есть несколько сценариев с разными паттернами нагрузки:
- **Команды (Commands):** Создание заказа, отмена заказа, изменение статуса, обновление платёжной информации, применение скидок, добавление купонов. Эти операции изменяют состояние системы, должны быть согласованными и транзакционными.
- **Запросы (Queries):** Получение заказа по ID, список заказов клиента, поиск заказов по дате/статусу, аналитические отчёты (количество заказов за период, сумма продаж, популярные товары), сложные фильтры с пагинацией, сортировкой, агрегацией.

Использование одной модели данных (CRUD) для обоих типов операций приводит к:
- Конфликту между оптимизацией записи (нормализованная схема) и чтения (денормализованная, с индексами, агрегациями).
- Риску блокировок при одновременной записи и чтении (особенно в аналитических запросах).
- Сложности масштабирования: нельзя независимо масштабировать чтение и запись.
- Ухудшению производительности при сложных отчётах и поиске (поскольку они работают с теми же таблицами, что и транзакционные операции).

Необходимо выбрать подход для разделения команд и запросов, который:
- Оптимизирует производительность каждой стороны.
- Позволяет масштабировать чтение и запись независимо.
- Интегрируется с Event Sourcing (ADR-016) и EDA (ADR-002).
- Упрощает построение сложных read-моделей (для отчётов, аналитики, поиска).
- Сохраняет согласованность данных (eventual consistency допустима).

---

## Решение

Внедряем **CQRS (Command Query Responsibility Segregation)** для **Order Service**.

**Команды** используют текущее состояние (агрегаты) и сохраняются в Event Store (ADR-016).  
**Запросы** используют отдельные проекции (read models), построенные из событий, оптимизированные для чтения.

**Схема:**
```
[ Command ] → [ Command Handler ] → [ Aggregate ] → [ Event Store (PostgreSQL) ]
                                                          │
                                                          ▼
                                                  [ Kafka (события) ]
                                                          │
                                                          ▼
                                                  [ Projection Service ]
                                                          │
                                                          ▼
[ Query ] → [ Query Handler ] → [ Read DB (PostgreSQL/ClickHouse) ] ← [ Read Model ]
```

**Детали:**
- **Command Side:** Обработка команд (CreateOrder, CancelOrder, UpdateStatus, ApplyDiscount). Использует Event Sourcing для хранения событий. Гарантирует консистентность (агрегаты).
- **Query Side:** Обработка запросов (GetOrder, ListOrders, SearchOrders, OrderAnalytics). Использует отдельную базу данных (PostgreSQL с денормализованными таблицами, индексами, материализованными представлениями или ClickHouse для аналитики).
- **Синхронизация:** Проекции обновляются асинхронно через Kafka (event-driven). Используем **eventual consistency** (допустимая задержка между записью и чтением — до 1–2 секунд для обычных запросов и до 5–10 минут для аналитических).
- **Read DB:** Денормализованные таблицы, оптимизированные под конкретные запросы. Например:
  - `orders_read` — все поля заказа (включая вычисляемые).
  - `order_items_read` — позиции заказа.
  - `orders_by_status` — материализованное представление для агрегации по статусам.
  - `orders_analytics` — агрегированные данные для отчётов.

---

## Архитектура CQRS (схема)

```
[ Клиент ]
    │
    ├── Команда (CREATE) → [ Command Handler ] → [ Aggregate ] → [ Event Store ]
    │
    └── Запрос (READ)   → [ Query Handler ]  → [ Read DB ] ← [ Projection Service ]
                                                      │
                                                      ▼
                                              [ Kafka (события) ]
```

## Пример реализации (команда и запрос)

**Команда:**

```go
type CreateOrderCommand struct {
    CustomerID string
    Items      []OrderItem
    Discount   *Discount
}

func (h *OrderCommandHandler) HandleCreateOrder(ctx context.Context, cmd CreateOrderCommand) error {
    order := domain.NewOrder(cmd.CustomerID, cmd.Items, cmd.Discount)
    event := order.GetEvent() // OrderCreated
    err := h.eventStore.Save(order.ID, event)
    if err != nil {
        return err
    }
    h.eventBus.Publish(event) // Kafka
    return nil
}
```

**Запрос:**

```go
type GetOrderQuery struct {
    OrderID string
}

func (h *OrderQueryHandler) HandleGetOrder(ctx context.Context, query GetOrderQuery) (*OrderDTO, error) {
    return h.readRepo.GetByID(query.OrderID)
}

type ListOrdersQuery struct {
    CustomerID string
    Status     string
    Limit      int
    Offset     int
}

func (h *OrderQueryHandler) HandleListOrders(ctx context.Context, query ListOrdersQuery) (*OrderListDTO, error) {
    return h.readRepo.List(query)
}
```

**Проекция (Read Model):**

```go
func (s *OrderProjection) OnOrderCreated(event OrderCreated) {
    readModel := &OrderRead{
        ID:          event.AggregateID,
        CustomerID:  event.CustomerID,
        Status:      "NEW",
        Items:       event.Items,
        TotalAmount: event.TotalAmount,
        CreatedAt:   event.Timestamp,
    }
    s.readRepo.Save(readModel)
}
```

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **CRUD (одна модель)** | Простота, единая БД, синхронная консистентность | Конфликт оптимизации, блокировки, сложность масштабирования | Не подходит для сложных аналитических запросов и роста нагрузки |
| **CQRS без Event Sourcing** | Разделение моделей, проще чем с ES | Нет аудита, сложнее синхронизировать изменения | У нас уже есть ES, CQRS с ним сочетается идеально |
| **CQRS только для аналитики** | Разделение только для отчётов | Сложность поддержки двух подходов | Мы хотим единообразного разделения для всех запросов (и простых, и аналитических) |

## Последствия

### Положительные
- ✅ Оптимизация каждой стороны: команды — быстрые транзакционные, запросы — гибкие и производительные.
- ✅ Независимое масштабирование: можно увеличить количество реплик Query Side, не затрагивая Command Side.
- ✅ Чёткое разделение ответственности в коде (чистая архитектура).
- ✅ Лёгкость построения проекций для разных видов запросов (детальные, агрегированные, аналитические).
- ✅ Поддержка сложных read-моделей (поиск, отчёты, аналитика).
- ✅ Естественная интеграция с Event Sourcing (события строят read-модели).

### Отрицательные
- ❌ Усложнение архитектуры (два хранилища, асинхронная синхронизация).
- ❌ Eventual consistency (задержка до секунды для обычных запросов, до минут для аналитики) — недопустимо для некоторых сценариев (например, сразу после создания заказа клиент хочет видеть его в списке).
- ❌ Дополнительная инфраструктура (Projection Service, Read DB, Kafka).
- ❌ Сложность отладки и мониторинга (задержки проекций, ошибки синхронизации).

### Компромиссы
- Для критических сценариев (например, GetOrder сразу после CreateOrder) используем **синхронную проекцию** или **кэширование** в Redis (чтобы данные были доступны мгновенно).
- Для аналитических отчётов допустима задержка до 5–10 минут (используем batch-обновления).
- Read DB проектируем с учётом типовых запросов (индексы, денормализация, материализованные представления).
- Внедряем мониторинг задержек проекций (метрики в Prometheus).

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с CQRS |
|-------------------|---------------------|
| **Event Sourcing** | События из Event Store строят read-модели. |
| **EDA** | События публикуются в Kafka для проекций. |
| **Saga** | Команды Saga могут быть частью Command Side; статус саги читается через Query Side. |
| **Circuit Breaker / Retry** | Защита запросов к Read DB. |
| **Ambassador** | Внешние интеграции (например, получение данных из внешних систем для проекций). |
| **Sidecar** | Логирование, метрики, трассировка для CQRS-компонентов. |
| **Service Mesh** | Управление трафиком между Command и Query Side при переходе на микросервисы. |
| **Абстрактные инструкции** | Инструкции могут быть частью команд и запросов (через REST/gRPC). |
