# ADR-006: Выбор брокера сообщений

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Система E‑Commerce использует событийно-ориентированную архитектуру (ADR-002). Необходим брокер для публикации и доставки событий между модулями (а позже — между микросервисами). Требования:

- **Высокая пропускная способность** — тысячи событий в секунду (заказы, платежи, уведомления).
- **Гарантии доставки** — at-least-once (минимум один раз) для критических событий (платежи, заказы).
- **Долговременное хранение событий** — возможность replay для восстановления проекций и отладки.
- **Поддержка масштабирования** — горизонтальное масштабирование, партиционирование, группы потребителей.
- **Интеграция с CDC** — необходимость публикации изменений из PostgreSQL через Debezium.
- **Поддержка абстрактных бизнес-инструкций** — события могут быть сложными контейнерами с инструкциями для координации Saga и CQRS.

Рассматривались:

1. **Apache Kafka** — распределённый, с долговременным хранением.
2. **RabbitMQ** — надёжный, с гибкой маршрутизацией.
3. **NATS** — лёгкий, быстрый, для микросервисов.
4. **AWS SQS/SNS** — управляемый сервис в облаке.

---

## Решение

Выбран **Apache Kafka** (версия 3.x) как основной брокер сообщений.

**Обоснование:**

- **Производительность:** Kafka обеспечивает высокую пропускную способность (миллионы сообщений/сек) и низкую задержку.
- **Долговременное хранение:** Сохранение событий на диске (с настраиваемым retention) позволяет replay и восстановление проекций.
- **Партиционирование:** Позволяет масштабировать обработку событий, увеличивая число партиций и потребителей.
- **Группы потребителей:** Обеспечивают горизонтальное масштабирование потребителей и отказоустойчивость.
- **Интеграция с Debezium:** Нативная поддержка CDC из PostgreSQL — изменения в БД автоматически публикуются в Kafka.
- **Экосистема:** Большое сообщество, инструменты мониторинга (Prometheus, Grafana), управление (Kafka Manager, Confluent Control Center).
- **Поддержка сложных событий:** Kafka не накладывает ограничений на формат сообщений — можно передавать JSON, Avro, Protobuf с любым содержимым (включая абстрактные инструкции для Saga и CQRS).

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
|--------------|-------|--------|-------------------|
| **RabbitMQ** | Гибкая маршрутизация, подтверждения доставки, простота | Сложнее с replay, меньше пропускная способность, нет долговременного хранения (сообщения удаляются после подтверждения) | Не подходит для replay событий и CDC |
| **NATS** | Лёгкий, быстрый, простота | Слабее с гарантиями доставки, нет долговременного хранения, меньше интеграций с CDC | Не подходит для наших требований к надёжности и replay |
| **AWS SQS/SNS** | Управляемый сервис, интеграция с AWS | Привязка к вендору, ограничения на размер сообщения, сложнее с replay | Мы хотим сохранить гибкость и избежать вендор-лока |

## Последствия

### Положительные
- ✅ Высокая пропускная способность и надёжность.
- ✅ Возможность replay событий для восстановления проекций и отладки.
- ✅ Масштабируемость через партиционирование.
- ✅ Интеграция с Debezium для CDC из PostgreSQL.
- ✅ Поддержка сложных событий с абстрактными инструкциями.
- ✅ Большое сообщество и инструменты мониторинга.

### Отрицательные
- ❌ Операционная сложность (настройка кластера, управление топиками, партициями, мониторинг лагов).
- ❌ Задержка (латентность) выше, чем у NATS, но допустима для асинхронных событий.
- ❌ Требуется управление схемами (Avro/Protobuf) для обеспечения совместимости версий событий.

### Компромиссы
- На старте используем **managed Kafka** (например, Confluent Cloud или MSK) для снижения операционной нагрузки.
- Внедряем **мониторинг** (лаги потребителей, ошибки, задержки) через Prometheus и Grafana.
- Используем **Protobuf** для сериализации событий (с поддержкой версионирования).
- Для критических событий (платежи) используем **именованные топики** с `min.insync.replicas=2` для гарантии доставки.

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Kafka |
|-------------------|---------------------|
| **EDA** | Kafka — основная шина событий |
| **CQRS** | События из Kafka строят read-модели (проекции) |
| **Event Sourcing** | Event Store может быть реализован на Kafka (или PostgreSQL с CDC в Kafka) |
| **Saga** | Оркестратор публикует события в Kafka; сервисы подписываются на них |
| **Абстрактные инструкции** | События могут содержать инструкции для координации бизнес-процессов |
| **CDC** | Debezium публикует изменения из PostgreSQL в Kafka |
| **Service Mesh** | Взаимодействие с Kafka остаётся неизменным при переходе на микросервисы |
