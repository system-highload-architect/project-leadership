# ADR-014: Выбор стратегии повторных попыток (Retry)

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Система E‑Commerce выполняет множество сетевых вызовов:
- **Внешние API** — платёжный шлюз, сервис уведомлений, сервис доставки, антифрод-сервисы.
- **База данных** — временные блокировки, deadlocks, перегрузка, сбои репликации.
- **Kafka** — временные ошибки продюсера/консьюмера, лидер-электорат, задержки.
- **Внутренние сервисы** (при переходе на микросервисы) — сетевые таймауты, ошибки gRPC.

Некоторые ошибки носят **временный характер** (сеть, перезагрузка сервиса, кратковременная перегрузка). Повторная попытка в таких случаях может привести к успеху.

Необходимо выбрать стратегию повторных попыток, которая:
- Повысит устойчивость системы.
- Не создаст дополнительной нагрузки на сервисы при сбоях.
- Будет работать совместно с Circuit Breaker.
- Позволит гибко настраивать параметры для разных типов вызовов.
- Учитывает идемпотентность операций.

---

## Решение

Внедряем стратегию повторных попыток с **экспоненциальной задержкой** и **джиттером** (случайное отклонение), используя библиотеку **`github.com/avast/retry-go`** или аналогичную.

**Параметры Retry (по умолчанию для внешних API):**

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| **Максимальное количество попыток** | 3 | Баланс между надёжностью и временем отклика |
| **Начальная задержка** | 100 мс | Быстрый повтор для кратковременных сбоев |
| **Множитель (factor)** | 2.0 | Экспоненциальный рост: 100 → 200 → 400 мс |
| **Максимальная задержка** | 5 секунд | Ограничение, чтобы не ждать слишком долго |
| **Джиттер** | ±30% | Случайное отклонение, чтобы избежать «эффекта стада» |
| **Типы ошибок для Retry** | Только временные ошибки (5xx, таймауты, сетевые ошибки) | Ошибки 4xx (Bad Request, Not Found) не повторяем |
| **Idempotency** | Все операции должны быть идемпотентными (или безопасными для повторения) | Гарантия того, что повтор не вызовет дублирование данных |
| **Backoff** | Экспоненциальный (2x) | Более эффективен, чем линейный или фиксированный |

**Настройки для разных типов вызовов:**

| Тип вызова | Попытки | Начальная задержка | Множитель | Макс. задержка |
|------------|---------|---------------------|-----------|----------------|
| **Платёжный шлюз** (критичный) | 3 | 200 мс | 2.0 | 5 сек |
| **Уведомления** (менее критичные) | 4 | 100 мс | 1.8 | 10 сек |
| **База данных (временные блокировки)** | 2 | 50 мс | 2.0 | 2 сек |
| **Kafka (продюсер)** | 5 | 100 мс | 2.0 | 10 сек |
| **Внутренние gRPC вызовы** | 2 | 50 мс | 2.0 | 2 сек |

**Дополнительно:**
- Retry реализуется через единую обёртку `retry.Do()` вместе с Circuit Breaker (в порядке: CB → Retry → Call).
- Логируем все попытки (attempt #1, #2, #3) для мониторинга и отладки.
- Экспортируем метрики (количество попыток, успех/неудача после retry) в Prometheus.
- Используем **контекст** для поддержки отмены и таймаутов.

## Альтернативы

| Стратегия | Плюсы | Минусы | Почему не выбрана |
|-----------|-------|--------|-------------------|
| **Без Retry** | Простота, мгновенный отказ | Снижает надёжность при временных сбоях | Неприемлемо для production |
| **Фиксированная задержка (Fixed Interval)** | Простая реализация | Может перегрузить сервис при большом количестве вызовов | Экспоненциальная даёт больше времени на восстановление |
| **Линейная задержка** | Более предсказуема, чем экспоненциальная | Медленнее восстанавливается при длительных сбоях | Экспоненциальная эффективнее |
| **Бесконечные попытки** | Максимальная надёжность | Может привести к бесконечному зависанию | Неприемлемо, нужно ограничение |

## Последствия

### Положительные
- ✅ Повышение устойчивости к временным сбоям.
- ✅ Уменьшение количества ошибок, возвращаемых пользователю.
- ✅ Экспоненциальная задержка + джиттер снижают нагрузку на сервисы при сбоях.
- ✅ Комбинация с Circuit Breaker даёт оптимальную защиту.
- ✅ Гибкая настройка для разных типов вызовов.
- ✅ Метрики и логи позволяют отслеживать эффективность Retry.

### Отрицательные
- ❌ Увеличение времени выполнения запросов (в худшем случае до 5–10 секунд).
- ❌ Необходимость обеспечивать идемпотентность операций.
- ❌ Сложность отладки (логирование всех попыток).
- ❌ Риск увеличения нагрузки на внешний сервис при большом количестве ошибок.

### Компромиссы
- Retry применяется только к **безопасным (идемпотентным)** операциям (GET, DELETE, идемпотентные POST/PUT с idempotency_key).
- Для критических операций (например, создание заказа) используем **Saga**, а не Retry (Saga управляет компенсацией).
- Количество попыток и задержки настраиваются **индивидуально** для каждого типа вызова (внешние API, БД, Kafka).

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Retry |
|-------------------|----------------------|
| **Circuit Breaker** | Retry + CB — стандартная комбинация. Сначала Retry (3 попытки), затем CB. |
| **Ambassador** | Retry может быть реализован внутри Ambassador (как политика для внешних вызовов). |
| **Sidecar** | Retry может быть реализован внутри Sidecar (для сквозной функциональности). |
| **Saga** | При сбое внешнего сервиса (платёжный шлюз) после исчерпания Retry, Saga может инициировать компенсацию. |
| **CQRS** | Retry применяется к запросам read-моделей (если они строятся из внешних данных). |
| **Kafka** | Retry для продюсера (временные ошибки лидера), но с осторожностью (не бесконечно). |
| **Graceful Degradation** | При невозможности выполнить операцию после Retry, система переходит в состояние частичной работоспособности (например, заказ создаётся, но платёж откладывается). |
