# ADR-013: Выбор стратегии Circuit Breaker

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Система E‑Commerce интегрируется с внешними сервисами:
- **Платёжный шлюз** (Payment Gateway) — обработка платежей, возвраты, холдирование.
- **Сервис уведомлений** (Notification Service) — отправка email, SMS, push-уведомлений.
- **Сервис доставки** (Delivery Service) — расчёт стоимости, отслеживание, создание заявок.
- **Сервис проверки контрагентов** (например, антифрод, скоринг).

Эти сервисы могут быть недоступны, перегружены или отвечать с большими задержками. Без защиты такие сбои могут привести к каскадным отказам («эффект снежного кома») — один медленный/недоступный сервис блокирует множество запросов, истощая ресурсы.

Необходимо выбрать стратегию защиты от подобных сбоев, которая:
- Предотвращает каскадные отказы.
- Ускоряет обнаружение проблем.
- Позволяет системе восстановиться при возвращении внешнего сервиса в рабочее состояние.

---

## Решение

Внедряем паттерн **Circuit Breaker** с использованием библиотеки **`github.com/sony/gobreaker`** (или аналогичной) на стороне клиента для каждого внешнего вызова.

**Параметры Circuit Breaker (для платёжного шлюза, критичного сервиса):**

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| **MaxFailures** | 5 | Количество ошибок за период, после которых CB переходит в Open |
| **Timeout** | 10 секунд | Время в Open перед переходом в Half-Open |
| **HalfOpenMaxCalls** | 3 | Количество пробных вызовов в Half-Open |
| **Тип ошибок** | Только 5xx и таймауты | Ошибки 4xx (Bad Request, Not Found) не считаются сбоями сервиса |
| **Период сбора ошибок** | 30 секунд | Окно, за которое считаются ошибки |

**Для менее критичных сервисов (уведомления, доставка):**

| Параметр | Значение |
|----------|----------|
| **MaxFailures** | 10 |
| **Timeout** | 30 секунд |
| **HalfOpenMaxCalls** | 5 |

**Дополнительно:**
- Логируем все переходы состояния Circuit Breaker (Closed → Open → Half-Open → Closed) с указанием причины.
- Экспортируем метрики (состояние, количество ошибок, время в Open) в Prometheus.
- Внедряем единый `Resiliency`-пакет, который оборачивает вызовы и автоматически применяет CB + Retry.
- Настраиваем алерты в Grafana при переходе в Open (чтобы оперативно реагировать).

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Без CB** | Простота | При сбое внешнего сервиса все вызовы будут ждать таймаут, ресурсы исчерпаются | Неприемлемо для production |
| **Retry without CB** | Повторные попытки могут помочь при временных сбоях | При длительной недоступности Retry только усугубляет ситуацию | Нужна комбинация CB + Retry |
| **Bulkhead** | Изоляция пулов потоков для разных сервисов | Требует управления пулами, сложнее в настройке | Добавляем позже, если CB не будет достаточно |
| **Timeouts Only** | Простота настройки | Не защищает от повторяющихся сбоев, ресурсы всё равно расходуются | Недостаточная защита |

## Последствия

### Положительные
- ✅ Защита от каскадных отказов.
- ✅ Быстрый отказ (fail-fast) при недоступности внешнего сервиса (пользователь получает понятную ошибку, а не бесконечную загрузку).
- ✅ Восстановление после сбоев (Half-Open).
- ✅ Прозрачность через метрики и логи.
- ✅ Снижение нагрузки на внешний сервис в момент сбоя.
- ✅ Алерты при переходе в Open позволяют оперативно реагировать.

### Отрицательные
- ❌ Усложнение кода (обёртки вокруг вызовов).
- ❌ Необходимость настройки порогов для каждого сервиса (индивидуально).
- ❌ Возможность ложных срабатываний (если пороги слишком низкие или ошибки 4xx включены).
- ❌ Требуется мониторинг состояния CB.

### Компромиссы
- Используем **единую конфигурацию** для всех внешних вызовов (пока не потребуется тонкая настройка) — для упрощения.
- Комбинируем CB с **Retry with Backoff** (экспоненциальная задержка) для повышения надёжности.
- Добавляем **мониторинг** состояния CB в Grafana.
- Внедряем **исключения для определённых ошибок** (4xx не считаем сбоями).

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Circuit Breaker |
|-------------------|-------------------------------|
| **Retry** | CB + Retry — стандартная комбинация. Сначала Retry (3 попытки), затем CB. |
| **Ambassador** | Circuit Breaker может быть реализован внутри Ambassador (как политика для внешних вызовов). |
| **Sidecar** | CB может быть реализован внутри Sidecar (для сквозной функциональности). |
| **Saga** | При сбое внешнего сервиса (платёжный шлюз) Saga может инициировать компенсацию, а не просто возвращать ошибку. |
| **CQRS** | CB защищает запросы к read-моделям (если они строятся из внешних данных). |
| **Service Mesh** | Service Mesh (Istio) может предоставлять встроенный Circuit Breaker (например, через DestinationRule). |
