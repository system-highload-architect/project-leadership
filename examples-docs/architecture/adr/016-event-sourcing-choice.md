# ADR-016: Выбор Event Sourcing для Order Service

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Система E‑Commerce использует событийно-ориентированную архитектуру (ADR-002) и CQRS (ADR-017). В рамках этих подходов возникает вопрос: **хранить ли события как источник истины (Event Sourcing)** или использовать традиционное хранение текущего состояния (CRUD) с публикацией событий.

**Преимущества Event Sourcing:**
- Полный аудит всех изменений.
- Возможность восстановления состояния на любой момент времени.
- Естественная интеграция с EDA (события уже есть).
- Лёгкость построения проекций (read models) для CQRS.

**Недостатки Event Sourcing:**
- Сложность реализации (event store, воспроизведение событий, версионирование).
- Большие объёмы данных (события накапливаются).
- Eventual consistency (задержки между записью и чтением через проекции).
- Требуется идемпотентность и версионирование событий.

В E‑Commerce ключевым агрегатом является **Order** (заказ). Его жизненный цикл включает несколько состояний (NEW, PAID, SHIPPED, DELIVERED, CANCELLED) и множество событий (создан, оплачен, отгружен, доставлен, отменён, изменён). Аудит изменений заказа критичен для бизнеса (финансовые операции, споры с клиентами, возвраты, налоговые проверки).

Кроме того, нам нужно поддерживать сложные бизнес-процессы (скидки, купоны, акции, отложенные платежи), для которых важно знать историю изменений и иметь возможность восстанавливать состояние на любой момент.

---

## Решение

**Event Sourcing внедряется для Order Service** (агрегат Order). Остальные сервисы (Payment, Inventory, Notification, User) используют традиционное хранение текущего состояния (CRUD) с публикацией событий.

**Обоснование:**

- **Аудит:** Заказы — это финансовые документы. Необходимо знать, кто, когда и почему изменил заказ (для разрешения споров, возвратов, налоговых проверок).
- **Восстановление:** Возможность восстановить состояние заказа на любой момент времени (например, для расследования инцидентов, отладки, воспроизведения ошибок).
- **CQRS:** Event Sourcing идеально сочетается с CQRS — проекции для чтения строятся из событий, что даёт гибкость и производительность.
- **Сложная бизнес-логика:** События позволяют моделировать процессы естественно (например, цепочка скидок, купонов, акций, изменение статусов).
- **Ограниченный объём:** Количество заказов растёт, но не экспоненциально, и события для заказов не слишком велики (несколько десятков событий на заказ). Для E‑Commerce это приемлемо.
- **Изоляция сложности:** Только один сервис (Order Service) использует Event Sourcing, что упрощает поддержку и не усложняет остальные сервисы.

**Техническая реализация:**
- Event Store: **PostgreSQL** (таблица `order_events` с полями: `order_id`, `event_type`, `event_data` (JSONB), `created_at`, `version`).
- Восстановление агрегата: при загрузке заказа читаем все события и применяем их к агрегату (в памяти с использованием `Apply()` методов).
- Снапшоты: периодически сохраняем текущее состояние заказа, чтобы не воспроизводить все события каждый раз (например, каждые 10 событий).
- Публикация событий: после сохранения события публикуем его в Kafka для других сервисов (проекции, уведомления, аналитика).
- Версионирование событий: используем `event_version` для поддержки обратной совместимости при изменении структуры событий.

## Архитектура Event Sourcing

```
[ Команда ] → [ Aggregate ] → [ Event Store (PostgreSQL) ] → [ Kafka ]
                                       │                           │
                                       ▼                           ▼
                                  [ Снапшот ]              [ Проекция (Read DB) ]
```

## Пример реализации (агрегат и события)

**Событие:**

```go
type Event interface {
    GetAggregateID() string
    GetTimestamp() time.Time
    GetType() string
    GetVersion() int
}

type OrderCreated struct {
    AggregateID string
    CustomerID  string
    Items       []OrderItem
    TotalAmount float64
    Timestamp   time.Time
    Version     int
}

type OrderPaid struct {
    AggregateID string
    PaymentID   string
    Amount      float64
    Timestamp   time.Time
    Version     int
}
```

**Агрегат:**

```go
type OrderAggregate struct {
    ID          string
    Status      string
    CustomerID  string
    Items       []OrderItem
    TotalAmount float64
    Payments    []Payment
    Version     int
}

func (a *OrderAggregate) Apply(event Event) {
    switch e := event.(type) {
    case *OrderCreated:
        a.ID = e.AggregateID
        a.Status = "NEW"
        a.CustomerID = e.CustomerID
        a.Items = e.Items
        a.TotalAmount = e.TotalAmount
        a.Version = e.Version
    case *OrderPaid:
        a.Status = "PAID"
        a.Payments = append(a.Payments, Payment{ID: e.PaymentID, Amount: e.Amount})
        a.Version = e.Version
    }
}

func (a *OrderAggregate) Replay(events []Event) {
    for _, event := range events {
        a.Apply(event)
    }
}
```

**Event Store (PostgreSQL):**

```sql
CREATE TABLE order_events (
    id SERIAL PRIMARY KEY,
    aggregate_id UUID NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    event_data JSONB NOT NULL,
    event_version INTEGER NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_order_events_aggregate ON order_events(aggregate_id);
```

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Только CRUD + события** | Проще, меньше данных, быстрее чтение | Нет полного аудита, нельзя восстановить состояние на любой момент | Аудит заказов критичен для бизнеса (финансы, возвраты, споры) |
| **Event Sourcing для всех сервисов** | Единообразие, полный аудит для всех сущностей | Сложность для всех сервисов, избыточно для простых сущностей (товары, пользователи) | Только Order требует аудита и восстановления |
| **Event Sourcing через Kafka (log)** | Хранение событий в Kafka, replay через Kafka Streams | Сложность управления топиками, retention, консьюмерами, отсутствие ACID-гарантий | Избыточно для E‑Commerce, PostgreSQL проще и надёжнее |

## Последствия

### Положительные
- ✅ Полный аудит заказов (кто, когда, что изменил).
- ✅ Возможность восстановить состояние заказа на любой момент (для отладки, воспроизведения, анализа).
- ✅ Естественная интеграция с CQRS (проекции строятся из событий).
- ✅ Единый источник истины (события) для Order Service.
- ✅ Лёгкость добавления новых проекций (например, для аналитики, поиска, отчётов).
- ✅ Поддержка сложной бизнес-логики (скидки, купоны, акции) через цепочки событий.
- ✅ Возможность отката состояния (replay событий до определённой версии).

### Отрицательные
- ❌ Усложнение Order Service (дополнительная логика работы с событиями, версионирование).
- ❌ Хранение большого количества событий (может потребоваться архивация и очистка старых событий).
- ❌ Eventual consistency между записью и чтением (проекции обновляются асинхронно, до 1-2 секунд задержки).
- ❌ Необходимость версионирования событий (при изменении структуры).
- ❌ Повышенные требования к идемпотентности обработчиков событий.

### Компромиссы
- Внедряем **снапшоты** для ускорения загрузки агрегатов (каждые 10 событий).
- Используем **PostgreSQL** как Event Store (простота, знакомый инструмент, ACID-гарантии).
- Внедряем **мониторинг** размера таблицы событий и задержек проекций.
- Для критических операций (например, создание заказа) допускаем небольшое окно eventual consistency (до 1–2 секунд) и информируем об этом пользователя (например, «Заказ создаётся, статус обновится в течение минуты»).
- Версионируем события (например, `OrderCreatedV1`, `OrderCreatedV2`) для обратной совместимости.

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Event Sourcing |
|-------------------|-------------------------------|
| **CQRS** | Event Sourcing + CQRS — идеальное сочетание. События строят read-модели (проекции). |
| **EDA** | События публикуются в Kafka для других сервисов (уведомления, аналитика, проекции). |
| **Saga** | События Saga могут быть частью Event Sourcing (например, события шагов Saga сохраняются). |
| **Абстрактные инструкции** | Инструкции могут быть сохранены как события для аудита и восстановления. |
| **Snapshots** | Внедряем снапшоты для оптимизации загрузки агрегатов. |
| **Архивация** | Старые события архивируются в холодное хранилище (S3) для снижения нагрузки на БД. |
