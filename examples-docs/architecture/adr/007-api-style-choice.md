# ADR-007: Выбор стиля API (REST vs gRPC)

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Система E‑Commerce предоставляет API для:
- **Внешних клиентов** — веб-приложение (браузер), мобильные приложения (iOS/Android), сторонние интеграции (партнёры, платёжные шлюзы).
- **Внутренних сервисов** — взаимодействие между модулями (заказы, платежи, товары, уведомления) внутри монолита и, в перспективе, между микросервисами.

Требования к API:
- Высокая производительность (низкая задержка, высокая пропускная способность).
- Чёткая контрактная модель (версионирование, обратная совместимость).
- Удобство для внешних клиентов (браузеры, мобильные устройства).
- Поддержка стриминга данных (например, для событий или больших объёмов данных).
- Простота разработки и документирования.
- Поддержка гибких бизнес-инструкций (события-команды с абстрактными инструкциями).

Рассматривались:
1. **RESTful API (HTTP/1.1 + JSON)** — классический подход.
2. **gRPC (HTTP/2 + Protobuf)** — высокопроизводительный, строгие контракты.
3. **GraphQL** — гибкие запросы для клиентов.
4. **Гибридный подход** — REST для внешних, gRPC для внутренних.

---

## Решение

Принят **гибридный подход**:

- **Для внешних API (публичных)** — **RESTful API** (OpenAPI 3.0, JSON).
- **Для внутренних сервисов** — **gRPC** (Protobuf).

**Обоснование:**

### REST для внешних API:
- **Простота и привычность** — фронтенд-разработчики (React, мобильные приложения) хорошо знакомы с REST.
- **Отличная поддержка браузерами** — кэширование (HTTP-кэш, CDN), легко тестировать через браузер (curl, Postman).
- **Документирование** — OpenAPI/Swagger даёт интерактивную документацию.
- **Гибкость версионирования** — через URL (`/v1/orders`).
- **Поддержка сложных инструкций** — в теле запроса можно передавать JSON с абстрактными инструкциями (например, для Saga).

### gRPC для внутренних сервисов:
- **Высокая производительность** — бинарный протокол (Protobuf) эффективнее JSON (~5–10 раз быстрее сериализация, меньше размер сообщений). HTTP/2 даёт мультиплексирование, снижая задержку.
- **Строгие контракты** — Protobuf — строго типизированный язык описания интерфейсов, автоматическая генерация клиентов и серверов на Go, Java, Python и т.д.
- **Поддержка стриминга** — 4 типа вызовов: унарный, серверный стрим, клиентский стрим, двунаправленный стрим. Это критично для потоковых событий (заказы, платежи, уведомления).
- **Интеграция с EDA и абстрактными инструкциями** — события-команды могут передаваться по gRPC между модулями, сохраняя контракты.

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
|--------------|-------|--------|-------------------|
| **Только REST** | Простота, универсальность | Низкая производительность для внутренних вызовов, нет стриминга, JSON-сериализация тяжелее | Недостаточно эффективен для микросервисов |
| **Только gRPC** | Высокая производительность, стриминг | Сложность для внешних клиентов (браузеры, мобильные), нет HTTP-кэширования | Внешние клиенты будут испытывать трудности |
| **GraphQL** | Гибкость запросов (клиент выбирает поля) | Сложность реализации, кэширование, перегрузка БД | Избыточен для E‑Commerce, добавляет сложность без явной выгоды |

---

## Последствия

### Положительные
- ✅ Внешние клиенты получают простой и понятный REST API.
- ✅ Внутренние сервисы общаются быстро и надёжно через gRPC.
- ✅ Чёткие контракты для каждого стиля.
- ✅ Возможность миграции части внешних запросов на GraphQL в будущем (если потребуется).
- ✅ Поддержка абстрактных инструкций через JSON в REST и Protobuf в gRPC.

### Отрицательные
- ❌ Поддержка двух стилей API — дополнительная сложность разработки и документирования.
- ❌ Требуется управление двумя наборами контрактов (OpenAPI + Protobuf).
- ❌ Необходимость в шлюзе для трансляции gRPC в REST (если внешние клиенты захотят использовать gRPC).

### Компромиссы
- Используем **gRPC Gateway** для автоматической генерации REST-эндпоинтов из Protobuf (упрощает поддержку).
- Документируем оба API через OpenAPI и Protobuf-комментарии.
- Внедряем единую систему аутентификации (JWT), общую для обоих стилей.
- Для внешних интеграций (платёжные шлюзы) используем REST (так как они обычно предоставляют REST API).

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с выбором API |
|-------------------|---------------------------|
| **EDA** | События могут приходить через REST (внешние webhooks) или через gRPC (внутренние события) |
| **CQRS** | Команды → gRPC (внутренние), Запросы → REST (внешние) или gRPC (внутренние) |
| **Saga** | Оркестратор может принимать команды через REST (внешний триггер) и управлять через gRPC |
| **Абстрактные инструкции** | Инструкции передаются в теле REST-запроса (JSON) или в gRPC-сообщении (Protobuf) |
| **API Gateway** | Единая точка входа для внешних клиентов, которая маршрутизирует REST-запросы к внутренним gRPC-сервисам (через gRPC Gateway) |
| **Service Mesh** | Управление трафиком gRPC между микросервисами |
