# ADR-018: Выбор Strangler Pattern для эволюционной миграции

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Система E‑Commerce начинается как **модульный монолит** (ADR-001). Однако в будущем, по мере роста команды, нагрузки и сложности бизнес-логики, может потребоваться переход к **микросервисной архитектуре** (ADR-003). Такой переход — это сложный и рискованный процесс, особенно если пытаться сделать его «за один раз» (big bang).

Необходимо выбрать стратегию миграции, которая позволит:
- Постепенно выносить функциональность из монолита в отдельные сервисы.
- Минимизировать риски и простои.
- Сохранить работоспособность системы на всех этапах.
- Обеспечить возможность отката на любом этапе.
- Сохранить гибкость бизнес-логики (абстрактные инструкции, Saga, CQRS, Event Sourcing) при миграции.
- Интегрироваться с существующей инфраструктурой (Kafka, API Gateway, Service Mesh).

---

## Решение

Принята стратегия **Strangler Pattern** (паттерн «Душитель») для эволюционной миграции монолита к микросервисам.

**Этапы миграции:**

1. **Создание API Gateway** — единая точка входа для всех клиентов, которая будет маршрутизировать запросы либо к монолиту, либо к новым сервисам.

2. **Выделение первого сервиса** (например, Payment Service) — реализуем его как отдельный микросервис, а API Gateway направляет запросы к нему. Монолит продолжает работать для остальной функциональности.

3. **Переключение трафика** — постепенно увеличиваем процент запросов, направляемых на новый сервис (canary release), мониторим ошибки и производительность.

4. **Выделение следующих сервисов** — повторяем процесс для Inventory, Notification, User, Product и т.д.

5. **Удаление функциональности из монолита** — когда новый сервис полностью заменит старую функциональность, удаляем соответствующий код из монолита.

6. **Полный переход** — монолит становится либо «ядром» (базовые сервисы), либо полностью заменяется набором микросервисов.

**Инструменты:**
- **API Gateway:** Envoy или KrakenD (лёгкий, быстрый, поддерживает маршрутизацию по заголовкам/путям).
- **Feature Flags:** Используем LaunchDarkly или самодельную реализацию для гибкого переключения трафика.
- **Мониторинг:** Prometheus + Grafana для отслеживания ошибок и задержек при переключении трафика.
- **Service Mesh:** Istio или Linkerd для управления трафиком, безопасности и наблюдаемости (на этапе 3–4).
- **Kafka:** Остаётся единой шиной событий как для монолита, так и для новых сервисов.

## План миграции по модулям (пример для E‑Commerce)

| Очередность | Модуль | Причина | Ожидаемый срок |
|-------------|--------|---------|----------------|
| 1 | **Payment** | Высокая нагрузка, критичность, необходимость изоляции сбоев | Этап 3 (Q1 2027) |
| 2 | **Inventory** | Рост данных, требуется независимое масштабирование | Этап 3 (Q1 2027) |
| 3 | **Notification** | Слабая связанность, легко выделить, нагрузка растёт | Этап 3 (Q1 2027) |
| 4 | **Product** | Чёткие границы, частые изменения каталога | Этап 4 (Q2 2027) |
| 5 | **User** | Меньше изменений, можно оставить в монолите дольше | Опционально |

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Big Bang (полная перезапись)** | Единообразие, отсутствие промежуточных состояний | Высокий риск, длительный простой, сложность тестирования | Слишком рискованно для production |
| **Strangler Pattern** | Безопасная миграция, возможность отката, постоянная работоспособность | Требует дополнительной инфраструктуры (Gateway, Feature Flags), затянутый процесс | Выбран, так как минимизирует риски |
| **Parallel Run (запуск двух систем параллельно)** | Возможность сравнения результатов | Удвоение нагрузки и затрат на инфраструктуру | Избыточно для E‑Commerce |

## Последствия

### Положительные
- ✅ Безопасная миграция без простоев.
- ✅ Возможность отката на любом этапе.
- ✅ Постепенное обучение команды микросервисам.
- ✅ Гибкость — можно переключать трафик по пользователям/фичам.
- ✅ Сохранение единой событийной шины (Kafka) для бесшовной интеграции монолита и микросервисов.
- ✅ Возможность миграции с сохранением абстрактных инструкций, Saga, CQRS (они остаются неизменными).

### Отрицательные
- ❌ Усложнение архитектуры (дополнительный слой — API Gateway).
- ❌ Длительность процесса (миграция может занять 6–12 месяцев).
- ❌ Необходимость поддерживать обратную совместимость между старой и новой версиями API.
- ❌ Возможный рост задержек при маршрутизации через Gateway.

### Компромиссы
- Начинаем миграцию с **самого простого и изолированного модуля** (Notification Service), чтобы наработать опыт.
- Используем **Feature Flags** для постепенного переключения пользователей.
- Внедряем **сквозное тестирование** (e2e) для проверки работы Gateway и нового сервиса.
- Для критических модулей (Payment) используем **канареечные релизы** (1% → 10% → 50% → 100% трафика).
- Сохраняем **единую шину событий** (Kafka) как для монолита, так и для микросервисов.

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Strangler |
|-------------------|--------------------------|
| **API Gateway** | Основной инструмент для маршрутизации запросов. |
| **Service Mesh** | Управление трафиком между монолитом и микросервисами. |
| **Feature Flags** | Гибкое переключение трафика без передеплоя. |
| **EDA (Kafka)** | Единая шина событий для монолита и микросервисов. |
| **Saga** | Saga остаётся неизменной (оркестратор может быть вынесен в отдельный сервис). |
| **CQRS / Event Sourcing** | Могут быть вынесены вместе с модулем (например, Order Service). |
| **Ambassador** | Внешние интеграции могут быть переиспользованы как для монолита, так и для микросервисов. |
| **Sidecar** | Сквозная функциональность (логи, метрики, трассировка) остаётся единой. |
