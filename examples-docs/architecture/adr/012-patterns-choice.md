# ADR-012: Выбор архитектурных паттернов

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

Для реализации E‑Commerce платформы необходимо выбрать набор архитектурных паттернов, которые обеспечат:
- **Слабость связанности** модулей.
- **Тестируемость** и поддерживаемость.
- **Масштабируемость** и эволюционность.
- **Надёжность** при интеграциях с внешними системами.
- **Гибкость бизнес-логики** — возможность изменять процессы без переписывания кода.
- **Готовность к переходу на микросервисы** (Strangler Pattern).

Паттерны должны покрывать:
- Организацию кода внутри модулей.
- Коммуникацию между модулями.
- Работу с данными и событиями.
- Устойчивость к сбоям и распределённые транзакции.
- Сквозную функциональность (логирование, метрики, трассировка).

---

## Решение

Выбраны следующие архитектурные паттерны, адаптированные для E‑Commerce платформы:

### 1. **Модульный монолит** (стартовая архитектура)
- **Связь:** ADR-001.
- **Применение:** Все модули (Product, Order, Payment, User, Notification) находятся в одной кодовой базе, но с чёткими границами.
- **Обоснование:** Быстрый старт, простота транзакций, готовность к выделению.

### 2. **Clean Architecture** — для организации кода внутри каждого модуля
- **Связь:** ADR-004.
- **Слои:** Domain → Use Cases → Delivery → Infrastructure.
- **Обоснование:** Тестируемость, гибкость, готовность к микросервисам.

### 3. **Event-Driven Architecture (EDA)** — для коммуникации между модулями
- **Связь:** ADR-002.
- **Брокер:** Kafka (ADR-006).
- **Обоснование:** Слабая связанность, асинхронность, аудит, поддержка абстрактных инструкций.

### 4. **CQRS (Command Query Responsibility Segregation)** — для разделения команд и запросов
- **Связь:** ADR-017.
- **Применение:** Внутри модуля Order (для сложных запросов) и для аналитики.
- **Обоснование:** Оптимизация чтения и записи, гибкость запросов, поддержка проекций.

### 5. **Event Sourcing** — для хранения событий как источника истины
- **Связь:** ADR-016.
- **Применение:** Внутри модуля Order (аудит, восстановление состояния).
- **Обоснование:** Полный аудит, возможность восстановления на любой момент, естественная интеграция с EDA и CQRS.

### 6. **Saga (Orchestration + Choreography)** — для распределённых транзакций
- **Связь:** ADR-015.
- **Оркестратор:** Управляет процессом (например, создание заказа → платёж → резервирование → уведомление).
- **Хореография:** Внутренние шаги (например, уведомления) — через события.
- **Обоснование:** Гибкость, контроль, слабая связанность внутренних шагов.

### 7. **Circuit Breaker** — для защиты от каскадных сбоев
- **Связь:** ADR-013.
- **Применение:** При вызове внешних сервисов (платёжный шлюз, уведомления, доставка).
- **Обоснование:** Защита от сбоев, быстрый отказ, восстановление.

### 8. **Retry with Backoff** — для устойчивости к временным сбоям
- **Связь:** ADR-014.
- **Применение:** При работе с сетью, БД, Kafka, внешними API.
- **Обоснование:** Повышение надёжности, снижение количества ошибок, возвращаемых пользователю.

### 9. **Sidecar** — для выноса сквозной функциональности
- **Связь:** ADR-020.
- **Применение:** Логирование, метрики, трассировка (OpenTelemetry), Health Checks.
- **Обоснование:** Единообразие, независимость от языка, лёгкость обновления.

### 10. **Ambassador** — для управления внешними интеграциями
- **Связь:** ADR-019.
- **Применение:** Платёжный шлюз, сервис уведомлений, доставка.
- **Обоснование:** Единые политики (Retry, Circuit Breaker, кэширование, аутентификация).

### 11. **Strangler Pattern** — для постепенной замены устаревших модулей
- **Связь:** ADR-018.
- **Применение:** При переходе от монолита к микросервисам.
- **Обоснование:** Безопасная миграция, возможность отката.

### 12. **Service Mesh** — для управления трафиком и безопасностью при переходе на микросервисы
- **Связь:** ADR-003, ADR-022 (будет добавлен).
- **Применение:** При переходе на микросервисы.
- **Обоснование:** Управление трафиком, безопасность (mTLS), наблюдаемость.

### 13. **Абстрактные бизнес-инструкции** (Saga + EDA + CQRS) — для гибкой бизнес-логики
- **Применение:** Сложные бизнес-процессы (например, создание заказа со скидками, купонами, трекингом).
- **Обоснование:** Бизнес-логика описывается декларативно, а не императивно, что делает систему гибкой и эволюционирующей.

## Альтернативы

| Паттерн | Альтернатива | Почему выбрано |
|---------|--------------|----------------|
| Clean Architecture | Layered (n-tier) | Clean даёт лучшую тестируемость и гибкость |
| EDA | Синхронные REST/gRPC вызовы | EDA даёт слабую связанность и аудит |
| CQRS | CRUD | CQRS необходим для сложных read-моделей (отчёты, поиск) |
| Event Sourcing | CRUD + события | Event Sourcing даёт полный аудит и восстановление |
| Saga | Двухфазный коммит (2PC) | 2PC не масштабируется, Saga — стандарт для распределённых систем |
| Circuit Breaker | Без защиты | Circuit Breaker обязателен для внешних интеграций |
| Retry | Без повторных попыток | Повышает устойчивость системы |
| Sidecar | Встраивание логирования в код | Sidecar упрощает обновление сквозных функций |
| Ambassador | Прямые вызовы без прокси | Ambassador централизует управление интеграциями |
| Strangler | Полная перезапись системы | Strangler снижает риски миграции |
| Service Mesh | Без Service Mesh | Service Mesh даёт управление трафиком и безопасностью |

## Последствия

### Положительные
- ✅ Слабая связанность, лёгкость изменения и расширения.
- ✅ Высокая тестируемость (Clean Architecture, CQRS).
- ✅ Надёжность (Circuit Breaker, Retry, Saga).
- ✅ Единый стиль кода во всех модулях.
- ✅ Гибкость бизнес-логики (абстрактные инструкции).
- ✅ Готовность к микросервисам (Strangler Pattern).
- ✅ Сквозная наблюдаемость (Sidecar, Service Mesh).

### Отрицательные
- ❌ Увеличение сложности (больше паттернов → больше кода и конфигурации).
- ❌ Требуется обучение команды работе с EDA, CQRS, Saga, абстрактными инструкциями.
- ❌ Операционная сложность (Kafka, Service Mesh, Sidecar).

### Компромиссы
- CQRS внедряем только для read-интенсивных сценариев (не для всех модулей).
- Saga используем только для критических распределённых транзакций.
- Event Sourcing внедряем только для Order Service (аудит).
- Circuit Breaker и Retry реализуем через `go-resiliency` или аналоги.
- Абстрактные инструкции внедряем постепенно, начиная с простых сценариев.
