# ADR-008: gRPC vs REST для внутренних сервисов

**Статус:** Принято  
**Дата:** 2026-07-26  
**Автор:** Tech Lead / Архитектор

---

## Контекст

В рамках гибридного подхода к API (ADR-007) для внутренней коммуникации между модулями E‑Commerce необходим эффективный и надёжный протокол. Требования к внутреннему API:

- **Высокая производительность** — тысячи запросов/сек, низкая задержка (критично для заказов и платежей).
- **Строгие контракты** — предотвращение breaking changes, автоматическая генерация клиентов.
- **Поддержка стриминга** — для передачи потоков событий (например, уведомления, аналитика) и больших объёмов данных (экспорт заказов).
- **Простота реализации** на Go (основном языке бэкенда).
- **Интеграция с EDA и абстрактными инструкциями** — возможность передавать сложные события-команды с инструкциями для Saga и CQRS.
- **Интеграция с существующей инфраструктурой** (Kubernetes, Service Mesh, мониторинг).

Рассматривались:

1. **REST over HTTP/1.1 (JSON)**
2. **gRPC over HTTP/2 (Protobuf)**

---

## Решение

Выбран **gRPC** (с Protobuf) как основной протокол для внутренних сервисов.

**Обоснование:**

- **Производительность:** Protobuf эффективнее JSON (~5–10 раз быстрее сериализация, меньше размер сообщений). HTTP/2 даёт мультиплексирование, снижая задержку.
- **Контракты:** Protobuf — строго типизированный язык описания интерфейсов, автоматическая генерация клиентов и серверов на Go, Java, Python и т.д.
- **Стриминг:** gRPC поддерживает 4 типа вызовов: унарный, серверный стрим, клиентский стрим, двунаправленный стрим. Это критично для потоковых событий (заказы, платежи, уведомления).
- **Инструментарий:** Отличная интеграция с Kubernetes (gRPC-зеркалирование, Load Balancing через Headless Services), с Prometheus (метрики, трейсинг через OpenTelemetry).
- **Экосистема:** Поддержка gRPC Gateway для автоматической генерации REST API из Protobuf (для внешних клиентов, если потребуется).
- **Поддержка сложных событий:** Protobuf-сообщения могут содержать любые структуры данных, включая абстрактные инструкции для Saga и CQRS. Это позволяет передавать события-команды с гибким содержимым.

## Альтернативы

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
|--------------|-------|--------|-------------------|
| **REST over HTTP/1.1** | Простота, привычность, отладка через curl/браузер | JSON тяжёлый, HTTP/1.1 без мультиплексирования, нет встроенного стриминга, контракты через OpenAPI (менее строгие) | Недостаточно производительный, слабые контракты |
| **gRPC-Web** | gRPC для браузеров | Ограниченная поддержка стриминга, сложнее с кэшированием | Нам не нужен gRPC для внешних клиентов |

## Последствия

### Положительные
- ✅ Высокая производительность и низкая задержка.
- ✅ Строгие контракты, минимальный риск breaking changes.
- ✅ Поддержка стриминга для событийных потоков.
- ✅ Лёгкая интеграция с Kubernetes (сервис-дискавери, балансировка).
- ✅ Автоматическая генерация клиентов и документации (через Protobuf).
- ✅ Поддержка сложных событий с абстрактными инструкциями (Saga, CQRS, EDA).

### Отрицательные
- ❌ Более сложная отладка (требуется инструмент типа `grpcurl`, нет возможности просто открыть в браузере).
- ❌ Обучение команды Protobuf и gRPC (небольшой, но есть).
- ❌ HTTP/2 в некоторых сетевых окружениях может требовать дополнительной настройки.

### Компромиссы
- Внедряем **gRPC Gateway** для автоматической генерации REST API из Protobuf (для внешних клиентов, если потребуется).
- Используем `reflection` для возможности вызова gRPC через `grpcurl`.
- Добавляем **метрики и трейсинг** (OpenTelemetry) для наблюдаемости.
- Для отладки используем **gRPC-интерфейсы** с поддержкой логирования всех входящих/исходящих сообщений.

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с gRPC |
|-------------------|---------------------|
| **EDA** | События могут передаваться по gRPC между модулями (например, команды от оркестратора Saga) |
| **CQRS** | Команды — gRPC (запись), Запросы — gRPC (чтение) для внутренних сервисов |
| **Event Sourcing** | События могут передаваться по gRPC для синхронизации проекций |
| **Saga** | Оркестратор управляет шагами через gRPC-вызовы к сервисам |
| **API Gateway** | gRPC Gateway транслирует REST-запросы во внутренние gRPC-вызовы |
| **Service Mesh** | gRPC хорошо интегрируется с Istio/Linkerd для управления трафиком и безопасностью |
| **Абстрактные инструкции** | Protobuf-сообщения могут содержать инструкции для координации бизнес-процессов (Saga + EDA + CQRS) |
