
**Реализация Sidecar:**
- Запускается как **второй контейнер** в Kubernetes Pod'е (на старте — в монолите как отдельный процесс, позже — как sidecar-контейнер).
- Принимает метрики, логи и трассировку через **localhost** (UDP/HTTP) или Unix socket.
- Предоставляет **HTTP-эндпоинты** для health checks (`/live`, `/ready`), которые агрегируют состояние сервиса.
- Управляет конфигурацией (подгружает изменения из ConfigMap и перезагружает сервис через сигналы или HTTP-эндпоинт).
- Выполняет аутентификацию (проверяет JWT и пробрасывает контекст в сервис через заголовки).
- Логирует все входящие/исходящие запросы с TraceID и добавляет бизнес-контекст (например, `order_id`, `customer_id`).

**Инструменты:**
- **На старте** используем **самописный Sidecar на Go** (лёгкий, встраиваемый, часть инфраструктурного пакета), чтобы иметь полный контроль над логикой и быстро вносить изменения.
- **В перспективе** (при переходе на микросервисы) можем использовать **OpenTelemetry Collector** для сбора трейсов и метрик, **Prometheus** для метрик (sidecar экспортирует метрики на `/metrics`), **Vector** или **Fluent Bit** для сбора и отправки логов в Loki/Elasticsearch, **ConfigMap Reloader** для горячей перезагрузки конфигурации.

## Альтернативы

| Подход | Плюсы | Минусы | Почему не выбран |
|--------|-------|--------|------------------|
| **Встраивание логики в каждый сервис** | Простота, минимум инфраструктуры | Дублирование кода, сложность обновления, зависимость от языка | Неприемлемо для масштабирования |
| **Service Mesh (Istio/Linkerd)** | Мощное решение, уже включает sidecar (Envoy), даёт управление трафиком, безопасность и наблюдаемость | Избыточен для E‑Commerce на старте, сложность настройки, высокая ресурсоёмкость | Добавим позже при необходимости |
| **Ambassador (для внешних вызовов)** | Решает похожие задачи | Ambassador не решает внутреннюю сквозную функциональность (логирование, метрики, трассировка внутри сервисов) | Sidecar дополняет Ambassador |
| **DaemonSet на узле (агент)** | Один агент на узел, экономия ресурсов | Сложность изоляции, разные версии сервисов требуют разных версий агента | Sidecar даёт гибкость версионирования |

## Последствия

### Положительные
- ✅ Единая реализация сквозных функций для всех сервисов (независимо от языка).
- ✅ Лёгкость обновления — обновил sidecar, и все сервисы получили новую функциональность без пересборки.
- ✅ Независимость от языка — sidecar может быть написан на Go, а сервисы — на любом языке.
- ✅ Упрощение кода сервисов — они не знают о логировании, метриках, трассировке, аутентификации.
- ✅ Health checks агрегируются на уровне sidecar, что упрощает мониторинг в Kubernetes.
- ✅ Возможность горячей перезагрузки конфигурации без перезапуска сервиса.
- ✅ Единый контекст для трассировки и логирования (TraceID, бизнес-контекст).
- ✅ Поддержка сквозной наблюдаемости для абстрактных инструкций, Saga, CQRS, EDA.

### Отрицательные
- ❌ Увеличение потребления ресурсов (каждый Pod имеет два контейнера, дополнительная память и CPU).
- ❌ Усложнение отладки (логи и трейсы могут быть размазаны между сервисом и sidecar).
- ❌ Необходимость синхронизации версий sidecar и сервиса (версионирование).
- ❌ Дополнительная задержка (перехват запросов sidecar'ом, но обычно минимальная).

### Компромиссы
- На старте используем **один универсальный sidecar** для всех сервисов, с возможностью кастомизации через конфигурацию.
- Версионируем sidecar вместе с сервисом (в одном Helm-чарте), чтобы избежать несовместимости.
- Внедряем **мониторинг самого sidecar** (чтобы он не стал узким местом и не падал).
- Для критических сервисов (Order, Payment) sidecar настраивается с более строгими политиками логирования и трассировки.
- Используем **прокси-логирование** (sidecar логирует входящие/исходящие запросы, а сервис — только бизнес-логику).

## Связь с паттернами и будущими решениями

| Паттерн / Решение | Как связано с Sidecar |
|-------------------|------------------------|
| **EDA (Kafka)** | Sidecar логирует публикацию и потребление событий, добавляет TraceID и бизнес-контекст. |
| **Saga** | Sidecar логирует шаги Saga, передаёт контекст между шагами, трассирует выполнение. |
| **CQRS** | Sidecar логирует команды и запросы, добавляет контекст для отслеживания запросов. |
| **Event Sourcing** | Sidecar логирует сохранение событий, передаёт контекст для аудита. |
| **Абстрактные инструкции** | Sidecar логирует выполнение инструкций, добавляет контекст для трассировки. |
| **Ambassador** | Sidecar дополняет Ambassador (внешние вызовы логируются через Ambassador, внутренние — через Sidecar). |
| **Service Mesh** | Sidecar может быть заменён на Service Mesh (Envoy) при переходе на микросервисы, но логирование и метрики остаются. |
