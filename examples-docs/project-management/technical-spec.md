# Техническое задание: E‑Commerce Platform

**Версия:** 1.0 (MVP)  
**Дата:** 2026-07-26  
**Статус:** Черновик

---

## 1. Введение

### 1.1 Цель документа
Данный документ описывает функциональные и нефункциональные требования к E‑Commerce платформе, определяет архитектурные ограничения и критерии приемки. Он служит основой для разработки, тестирования и приемки MVP.

### 1.2 Краткое описание системы
E‑Commerce Platform — это интернет-платформа для малого и среднего бизнеса, позволяющая продавать товары онлайн, управлять заказами, принимать платежи и взаимодействовать с клиентами через уведомления.

Система предоставляет:
- Каталог товаров с категориями, фильтрами и поиском.
- Корзину покупок.
- Оформление заказов с выбором адреса доставки и способа оплаты.
- Интеграцию с платёжными шлюзами (банковские карты, СБП, PayPal).
- Управление заказами (статусы, история, отмена).
- Уведомления клиентов (email, SMS, push).
- Административную панель для управления товарами, заказами и пользователями.

### 1.3 Целевая аудитория
- **Операторы** — оформление заказов, управление заказами.
- **Менеджеры** — управление товарами, каталогом.
- **Администраторы** — управление пользователями, настройки, мониторинг.
- **Покупатели** — просмотр каталога, корзина, заказы.
- **Интеграторы** — подключение внешних систем через API.

## 2. Общие требования

### 2.1 Бизнес-цели
- Быстрый запуск MVP (3 месяца).
- Поддержка 1000+ заказов в день.
- Доступность 99.9%.
- Готовность к масштабированию и переходу на микросервисы.
- Гибкость бизнес-логики (возможность изменять процессы без переписывания кода).

### 2.2 Ограничения и допущения
- Первая версия работает как модульный монолит (ADR-001).
- Используется событийная модель (Kafka) для асинхронной коммуникации (ADR-002).
- База данных — PostgreSQL (ADR-005).
- Брокер сообщений — Kafka (ADR-006).
- API — гибридный: REST для внешних, gRPC для внутренних (ADR-007, ADR-008).
- Развёртывание — Kubernetes (k3s на старте, позже — managed).
- Язык бэкенда — Go, фронтенд — React + TypeScript.

## 3. Функциональные требования

### 3.1 Управление товарами
| ID | Функция | Описание |
|----|---------|----------|
| FR-01 | Просмотр каталога | Покупатель видит список товаров с пагинацией, фильтром по категории и поиском по названию. |
| FR-02 | Получение товара | Покупатель может посмотреть детальную информацию о товаре (описание, цена, наличие). |
| FR-03 | Создание товара | Администратор добавляет новый товар (название, описание, цена, категория, остаток, изображение). |
| FR-04 | Редактирование товара | Администратор изменяет данные товара. |
| FR-05 | Удаление товара | Администратор удаляет товар (только если нет активных заказов с ним). |
| FR-06 | Управление остатками | Автоматическое уменьшение остатка при создании заказа (через Inventory Service). |

### 3.2 Корзина
| ID | Функция | Описание |
|----|---------|----------|
| FR-07 | Добавление товара в корзину | Аутентифицированный пользователь добавляет товар с указанием количества. |
| FR-08 | Изменение количества | Пользователь изменяет количество товара в корзине. |
| FR-09 | Удаление товара из корзины | Пользователь удаляет позицию из корзины. |
| FR-10 | Просмотр корзины | Пользователь видит список товаров в корзине с итоговой суммой. |

### 3.3 Заказы
| ID | Функция | Описание |
|----|---------|----------|
| FR-11 | Создание заказа | Пользователь оформляет заказ из корзины (указывает адрес доставки, способ оплаты, применяет купон). Заказ создаётся в статусе NEW. |
| FR-12 | Получение заказа | Пользователь или администратор видит детали заказа (позиции, статус, сумма). |
| FR-13 | Список заказов | Пользователь видит список своих заказов с фильтром по статусу. |
| FR-14 | Отмена заказа | Пользователь отменяет заказ, если он ещё не оплачен и не отгружен. |
| FR-15 | Изменение статуса заказа | Администратор вручную меняет статус (SHIPPED, DELIVERED, CANCELLED). |
| FR-16 | Автоматическое обновление статуса | Система обновляет статус при получении событий (PaymentCompleted → PAID, OrderShipped → SHIPPED). |

### 3.4 Платежи
| ID | Функция | Описание |
|----|---------|----------|
| FR-17 | Инициация платежа | Система инициирует платёж для заказа (через платёжный шлюз). |
| FR-18 | Получение статуса платежа | Пользователь или система запрашивает статус платежа. |
| FR-19 | Обработка возврата | Администратор инициирует возврат средств (при отмене заказа или возврате товара). |
| FR-20 | Обработка холдирования | Для СБП поддерживается холдирование средств до подтверждения. |

### 3.5 Пользователи и аутентификация
| ID | Функция | Описание |
|----|---------|----------|
| FR-21 | Регистрация | Пользователь регистрируется по email и паролю. |
| FR-22 | Вход | Пользователь входит в систему (JWT). |
| FR-23 | Получение профиля | Пользователь получает свои данные. |
| FR-24 | Управление пользователями (админ) | Администратор просматривает и редактирует профили пользователей. |

### 3.6 Уведомления
| ID | Функция | Описание |
|----|---------|----------|
| FR-25 | Уведомление о создании заказа | Пользователь получает email/SMS с подтверждением. |
| FR-26 | Уведомление об изменении статуса | Пользователь получает уведомление при изменении статуса заказа (PAID, SHIPPED, DELIVERED, CANCELLED). |
| FR-27 | Уведомление о проблемах | Уведомление при сбое платежа или отмене заказа. |

## 4. Нефункциональные требования

### 4.1 Производительность и масштабируемость
| ID | Требование | Целевое значение |
|----|------------|------------------|
| NFR-01 | Время ответа API (p95) | < 200 мс для чтения, < 500 мс для записи |

### 4.2 Надёжность и доступность
| ID | Требование | Целевое значение |
|----|------------|------------------|
| NFR-05 | Доступность системы | 99.9% (SLO) |
| NFR-06 | Время восстановления (RTO) | 1 час |
| NFR-07 | Потери данных (RPO) | 15 минут |
| NFR-08 | Отказоустойчивость | Репликация БД, Kafka-кластер, Kubernetes-кластер |

### 4.3 Безопасность
| ID | Требование | Описание |
|----|------------|----------|
| NFR-09 | Аутентификация | JWT (Access + Refresh токены) |

### 4.4 Наблюдаемость
| ID | Требование | Описание |
|----|------------|----------|

### 4.5 Технические ограничения
- Язык бэкенда: Go (1.23+).
- База данных: PostgreSQL 15+.
- Брокер сообщений: Kafka 3.x.

- Контейнеризация: Docker + Kubernetes.
- CI/CD: GitHub Actions.

## 5. Критерии приемки

| № | Критерий | Способ проверки |
|---|----------|-----------------|
| 1 | Все эндпоинты API (OpenAPI) реализованы и работают | Postman-тесты, интеграционные тесты |
| 2 | События публикуются в Kafka при изменениях | Проверка наличия событий в топиках |
| 3 | UI позволяет выполнять все операции (каталог, корзина, заказы) | Ручное тестирование, E2E-тесты |
| 4 | Время ответа API < 200 мс при нагрузке 1000 запросов/сек | Нагрузочное тестирование (K6) |
| 5 | Система восстанавливается после сбоя за < 1 часа | Chaos-тестирование (убийство pod'ов) |
| 6 | Документация API и архитектурные диаграммы актуальны | Проверка reviewers |

## 6. Технические ограничения

- Все API версионируются (например, `/v1/`).
- Имена сущностей и полей — на английском языке (совместимость с кодом и документацией).
- Все изменения проходят code review и CI (автоматические проверки стиля, тесты, линтеры).
- Секреты и конфигурация хранятся в HashiCorp Vault / Kubernetes Secrets.

### Приложение B: Глоссарий
- **Агрегат** — корневая сущность (Order), обеспечивающая согласованность в рамках одного бизнес-процесса.
- **Событие (Event)** — факт изменения состояния (OrderCreated, PaymentCompleted).
- **Команда (Command)** — намерение изменить состояние (CreateOrder, CancelOrder).
- **Проекция (Read Model)** — денормализованная модель для чтения, построенная из событий.
- **Saga** — распределённая транзакция, состоящая из нескольких локальных шагов с компенсацией.
- **CQRS** — разделение команд и запросов (разные модели для записи и чтения).
- **Event Sourcing** — хранение всех изменений как последовательности событий.
