## 1. Введение

Данный документ описывает **Service Level Indicators (SLI)** и **Service Level Objectives (SLO)** для E‑Commerce платформы. Они определяют, как мы измеряем надёжность, производительность и доступность сервиса, и какие цели ставим перед собой.

SLO и SLI — это основа для принятия решений о масштабировании, улучшении кода и инфраструктуры, а также для коммуникации с бизнесом и стейкхолдерами.

В E‑Commerce платформе мы выделяем несколько критических сценариев:
- Просмотр каталога товаров.
- Добавление товаров в корзину.
- Оформление заказа.
- Обработка платежей.
- Обновление статуса заказов (через события).
- Административные операции (управление товарами, пользователями).

## 2. Определения

| Термин | Описание |
|--------|----------|
| **SLI** (Service Level Indicator) | Количественная метрика, измеряющая производительность или надёжность (например, время ответа, частота ошибок, доступность). |
| **SLO** (Service Level Objective) | Целевое значение для SLI (например, 99.9% доступность, 95% запросов < 200 мс). |
| **SLA** (Service Level Agreement) | Юридически обязывающее соглашение с клиентами (обычно на основе SLO). Для внутренних целей мы используем SLO. |

## 3. SLI (Service Level Indicators)

### 3.1 Доступность API (REST + gRPC)
**SLI:** Доля успешных запросов к API (HTTP 2xx / 4xx / 5xx).  
**Метод измерения:** Prometheus — `rate(http_requests_total{status!~"5.."}[5m]) / rate(http_requests_total[5m])`.

### 3.2 Задержка API (REST)
**SLI:** Время ответа REST API (p95, p99).  
**Метод измерения:** Prometheus — `histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))`.

### 3.3 Задержка gRPC (внутренние вызовы)
**SLI:** Время ответа gRPC-вызовов (p95, p99).  
**Метод измерения:** Prometheus — `histogram_quantile(0.95, rate(grpc_server_handling_seconds_bucket[5m]))`.

### 3.4 Частота ошибок API
**SLI:** Доля запросов, завершившихся с ошибкой (HTTP 5xx / gRPC error codes).  
**Метод измерения:** Prometheus — `rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])`.

### 3.5 Производительность БД (Write + Read + Event Store)
**SLI:** Время выполнения SQL-запросов (p95).  
**Метод измерения:** PostgreSQL `pg_stat_statements` или Prometheus-экспортер.

### 3.6 Задержка обработки событий (Kafka)
**SLI:** Задержка доставки событий (от публикации до получения подписчиком) для ключевых топиков (`orders`, `payments`, `notifications`).  
**Метод измерения:** Kafka consumer lag (разница между offset производителя и потребителя).

### 3.7 Доступность ключевых компонентов (Saga, Projection, Event Store)
**SLI:** Uptime критических компонентов (Saga Coordinator, Projection Service, Event Store).  
**Метод измерения:** Проверка health-эндпоинтов, мониторинг состояния pods.

### 3.8 Время восстановления агрегата (Event Sourcing)
**SLI:** Время, необходимое для восстановления агрегата Order из событий (p95).  
**Метод измерения:** Логирование времени выполнения `ReplayEvents()` в Order Service.

### 3.9 Успешность Saga
**SLI:** Доля успешно завершённых Saga (статус COMPLETED) от общего числа запущенных.  
**Метод измерения:** Метрика `saga_success_total / saga_total` в Prometheus.

## 4. SLO (Service Level Objectives)

### 4.1 Доступность API (REST + gRPC)
- **SLO:** 99.9% успешных запросов в месяц (≈ 8.76 часов простоя в год).
- **Измеряется за:** календарный месяц.

### 4.2 Задержка API (REST)
- **SLO для чтения (GET):** 95% запросов < 200 мс.
- **SLO для записи (POST, PUT, DELETE):** 95% запросов < 500 мс.
- **Измеряется за:** 5-минутные окна (rolling).

### 4.3 Задержка gRPC (внутренние вызовы)
- **SLO:** 95% gRPC-вызовов < 150 мс.
- **Измеряется за:** 5-минутные окна.

### 4.4 Частота ошибок API
- **SLO:** ошибки (HTTP 5xx / gRPC error codes) < 1% от всех запросов.
- **Измеряется за:** 5-минутные окна.

### 4.5 Производительность БД
- **SLO:** 95% SQL-запросов выполняются < 100 мс (чтение), < 200 мс (запись).

### 4.6 Задержка обработки событий (Kafka)
- **SLO:** 95% событий доставляются подписчикам за < 1 секунду.

### 4.7 Доступность критических компонентов
- **SLO:** Ключевые pods (backend, saga-coordinator, projection-service) имеют uptime ≥ 99.9% (за исключением планового обслуживания).

### 4.8 Время восстановления агрегата (Event Sourcing)
- **SLO:** p95 времени восстановления агрегата < 100 мс (для заказов с < 50 событий).

### 4.9 Успешность Saga
- **SLO:** Доля успешных Saga ≥ 99.5% (исключая бизнес-ошибки, например, недостаток товаров).

## 5. Методы измерения и инструменты

| SLI | Инструмент | Частота сбора | Где смотреть |
|-----|------------|---------------|--------------|
| Доступность API | Prometheus + Blackbox | Каждые 30 сек | Grafana: «API Availability» |
| Задержка API (REST) | Prometheus (histogram) | В реальном времени | Grafana: «Latency p95» |
| Задержка gRPC | Prometheus (histogram) | В реальном времени | Grafana: «gRPC Latency p95» |
| Ошибки API | Prometheus (counter) | В реальном времени | Grafana: «Error Rate» |
| Производительность БД | PostgreSQL + Prometheus exporter | Каждые 15 сек | Grafana: «DB Query Time» |
| Kafka lag | Kafka exporter + Prometheus | Каждые 30 сек | Grafana: «Kafka Consumer Lag» |
| Uptime pods | Kubernetes API + Prometheus | Каждые 30 сек | Grafana: «Pod Uptime» |
| Восстановление агрегата | Prometheus (histogram) | В реальном времени | Grafana: «Aggregate Replay Time» |
| Успешность Saga | Prometheus (counter) | В реальном времени | Grafana: «Saga Success Rate» |

## 6. Алерты и триггеры

| SLO | Порог для алерта | Действие |
|-----|------------------|----------|
| Доступность API | < 99.9% за 5 минут | Отправить алерт в Slack, начать диагностику |
| Задержка API (REST) | p95 > 500 мс для чтения / > 1000 мс для записи за 5 минут | Проверить БД, инфраструктуру, кэши |
| Задержка gRPC | p95 > 300 мс за 5 минут | Проверить сеть, нагрузку на сервисы |
| Ошибки API | > 2% за 5 минут | Изучить логи, эскалировать |
| Задержка БД | p95 > 200 мс за 5 минут | Проверить индексы, нагрузку, блокировки |
| Kafka lag | > 1000 сообщений за 5 минут | Проверить потребителей, увеличить партиции |
| Uptime pod | Pod не доступен более 2 минут | Перезапустить pod, проверить кластер |
| Восстановление агрегата | p95 > 500 мс | Проверить Event Store, оптимизировать запросы |
| Успешность Saga | < 99% за 5 минут (исключая бизнес-ошибки) | Проверить шаги Saga, логи ошибок |

Алерты отправляются в **Slack (#alerts)** и по **email** для on-call инженеров.

## 7. Окна для SLO

| SLO | Окно измерения | Допустимый бюджет ошибок |
|-----|----------------|--------------------------|
| Доступность 99.9% | Месяц | 43 минуты простоя в месяц |
| Доступность 99.9% | Квартал | 2.2 часа в квартал |
| Доступность 99.9% | Год | 8.76 часов в год |

Это означает, что мы можем позволить себе 43 минуты недоступности в месяц без нарушения SLO.

## 8. План улучшения SLO

- **Текущий уровень:** 99.9% доступности, p95 < 200 мс (чтение), p95 < 500 мс (запись).
- **Целевой уровень через 6 месяцев:** 99.95% доступности, p95 < 150 мс (чтение), p95 < 300 мс (запись).
- **Шаги для достижения:**
  - Улучшение мониторинга и алертинга.
  - Оптимизация SQL-запросов, индексов, партиционирование.
  - Внедрение кэширования (Redis) для частых запросов (каталог, корзина).
  - Масштабирование инфраструктуры (Kubernetes HPA, больше реплик).
  - Оптимизация восстановления агрегатов (Event Sourcing) через снапшоты.
  - Улучшение обработки событий (увеличение числа партиций, потребителей).
