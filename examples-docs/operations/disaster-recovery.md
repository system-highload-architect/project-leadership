# План восстановления после катастроф (DRP): E‑Commerce Platform

**Версия:** 1.0  
**Дата:** 2026-07-26  
**Статус:** Черновик

---

## 1. Введение

Данный документ описывает **план действий** при серьёзных сбоях, которые могут привести к длительной недоступности E‑Commerce платформы, потере данных или другим критическим последствиям.

**Цель:** Минимизировать время простоя (RTO) и потери данных (RPO), обеспечить восстановление системы в предсказуемые сроки.

В E‑Commerce платформе критическими компонентами являются:
- **Заказы и платежи** — финансовые операции.
- **Каталог товаров** — основа бизнеса.
- **Пользователи и аутентификация** — доступ к системе.
- **Событийная шина (Kafka)** — интеграция и асинхронная обработка.
- **Event Store (Order Service)** — история заказов для аудита и восстановления.

---

## 2. Ключевые показатели (RTO / RPO)

| Показатель | Целевое значение | Описание |
|------------|------------------|----------|
| **RTO** (Recovery Time Objective) | **1 час** | Максимальное время восстановления сервиса после катастрофы |
| **RPO** (Recovery Point Objective) | **15 минут** | Максимально допустимые потери данных (время с последнего бэкапа) |

---

## 3. Сценарии катастроф

| Сценарий | Описание | Влияние |
|----------|----------|---------|
| **Отказ всего кластера Kubernetes** | Полная недоступность всех сервисов | Критическое |
| **Отказ БД (PostgreSQL Write/Read/Event Store)** | Потеря основного инстанса, недоступность данных | Критическое |
| **Отказ брокера Kafka** | События не доставляются, потеря аудита и асинхронной обработки | Критическое |
| **Атака / компрометация** | Взлом, утечка данных, шифрование | Критическое |
| **Сбой облачного провайдера (регион)** | Недоступность всей инфраструктуры в регионе | Критическое |
| **Человеческая ошибка** | Удаление данных, неправильная конфигурация | Высокое / Критическое |
| **Сбой платёжного шлюза** | Невозможность обрабатывать платежи | Высокое |
| **Отказ Saga Coordinator** | Зависание распределённых транзакций | Высокое |

## 4. Стратегии восстановления

### 4.1 Отказ кластера Kubernetes

**Действия:**
1. Восстановить кластер из инфраструктурного кода (Terraform / GitOps).
2. Применить манифесты Kubernetes из репозитория (`kubectl apply -f k8s/`).
3. Восстановить данные из бэкапов (см. п. 5).
4. Проверить работоспособность health-эндпоинтов.
5. Переключить DNS на новый кластер.

**Примечание:** Для E‑Commerce критично быстро восстановить **Event Store** (таблицу `order_events`), чтобы не потерять историю заказов.

---

### 4.2 Отказ БД (PostgreSQL)

#### 4.2.1 Отказ Write DB (основная БД заказов, платежей, пользователей)

**Действия:**
1. Если есть реплика — повысить её до мастера (`promote`).
2. Если нет реплики — восстановить из последнего бэкапа (pg_dump / WAL).
3. Применить WAL-логи с момента последнего бэкапа (Point-in-Time Recovery).
4. Обновить строку подключения в ConfigMap / Secrets.
5. Перезапустить backend-поды для переподключения.

#### 4.2.2 Отказ Event Store (таблица `order_events`)

**Действия:**
1. Восстановить Event Store из бэкапа.
2. Проверить целостность событий (отсутствие дублей, корректные версии).
3. Если события потеряны безвозвратно — использовать снапшоты для восстановления агрегатов, а события перегенерировать из бизнес-логики (если возможно).

#### 4.2.3 Отказ Read DB (проекции для CQRS)

**Действия:**
1. Восстановить Read DB из бэкапа.
2. Если бэкап отсутствует — перестроить проекции из событий (replay из Kafka).
3. Оценить время перестроения (зависит от объёма событий). Если оно превышает RTO, восстановить из бэкапа.

---

### 4.3 Отказ брокера Kafka

**Действия:**
1. Если кластер Kafka мультиброкерный — переключиться на работающие брокеры.
2. Если все брокеры недоступны — восстановить из бэкапов топиков (kafka-dump).
3. Перезапустить продюсеров и консьюмеров.
4. Проверить, что нет потери событий (сравнить offsets).
5. Если события потеряны — использовать события из Event Store (PostgreSQL) для восстановления топиков.

**Для E‑Commerce критично:**
- Топик `orders` — события заказов (для Event Sourcing).
- Топик `payments` — события платежей (для Saga и проекций).

---

### 4.4 Атака / компрометация

**Действия:**
1. Изолировать систему (заблокировать сетевой доступ).
2. Сменить все секреты, пароли, токены (Vault / Kubernetes Secrets).
3. Восстановить систему из доверенных бэкапов.
4. Провести аудит безопасности и закрыть уязвимости.
5. Уведомить стейкхолдеров и регуляторов (при необходимости).

**Особенности для E‑Commerce:**
- Проверить, не скомпрометированы ли платёжные данные (если хранились).
- Уведомить пользователей о возможной утечке (по требованию регуляторов).

---

### 4.5 Сбой облачного провайдера (регион)

**Действия:**
1. Активировать резервный регион (если настроена мультирегиональность).
2. Переключить DNS на резервный регион (TTL < 5 минут).
3. Проверить работоспособность в резервном регионе.
4. Восстановить данные из крос-региональных бэкапов (если есть).

**Важно:** Для E‑Commerce критично, чтобы резервный регион имел свежие копии Event Store и Kafka (репликация через MirrorMaker 2.0).

---

### 4.6 Сбой платёжного шлюза

**Действия:**
1. Проверить доступность шлюза.
2. Если шлюз недоступен — включить режим «офлайн-платежей» (сбор заказов без оплаты с последующим подтверждением).
3. Уведомить клиентов о задержке обработки платежей.
4. Как только шлюз восстановится — обработать накопленные заказы.

---

### 4.7 Отказ Saga Coordinator

**Действия:**
1. Проверить состояние Saga в таблице `saga_state`.
2. Если Saga застряли в `IN_PROGRESS` — восстановить их вручную (повторить шаги или выполнить компенсацию).
3. Перезапустить Saga Coordinator.
4. Убедиться, что новые Saga создаются и выполняются корректно.

## 5. Резервное копирование (Backup Strategy)

| Компонент | Частота | Метод | Хранение | Восстановление |
|-----------|---------|-------|----------|----------------|
| **PostgreSQL (Write DB)** | Ежечасно (полный) + WAL (реалтайм) | pg_basebackup + WAL-архивация | S3 / облачный объектный сторедж | Point-in-Time Recovery (до 15 минут) |
| **PostgreSQL (Event Store)** | Ежечасно (полный) + WAL (реалтайм) | pg_basebackup + WAL-архивация | S3 | Point-in-Time Recovery (до 15 минут) |
| **PostgreSQL (Read DB)** | Ежечасно | pg_dump | S3 | Полное восстановление |
| **Kafka** | Ежедневно | kafka-dump / MirrorMaker 2.0 | S3 | Восстановление топиков (оффсеты) |
| **Redis** | Ежечасно | SAVE / BGSAVE | S3 | Восстановление из RDB-файла |
| **Конфигурация** | Каждое изменение | Git (Terraform + Kubernetes manifests) | GitHub | `kubectl apply -f` / Terraform apply |
| **Секреты** | Каждое изменение | HashiCorp Vault (зашифровано) | Vault + бэкап | Восстановить из Vault |

**Резервное копирование проверяется ежемесячно** — проводится тестовое восстановление на отдельном окружении.

**Особенности для E‑Commerce:**
- Бэкапы Event Store и Write DB должны быть синхронизированы по времени, чтобы восстановить согласованное состояние заказов и событий.
- Бэкапы Kafka должны включать все топики, используемые в EDA.

## 6. Процедура восстановления (пошагово)

1. **Активировать DRP:** Уведомить всех членов команды и стейкхолдеров.
2. **Диагностика:** Определить масштаб и причину катастрофы.
3. **Восстановление инфраструктуры:** Применить инфраструктурный код (Terraform, Kubernetes manifests).
4. **Восстановление данных:** Восстановить БД (Write, Read, Event Store), Kafka, Redis из бэкапов.
5. **Проверка:** Запустить smoke-тесты, проверить целостность данных (заказы, платежи, события).
6. **Переключение трафика:** Обновить DNS / Ingress на восстановленную систему.
7. **Мониторинг:** Наблюдать за системой, убедиться в стабильности.
8. **Постмортем:** Провести анализ инцидента и обновить DRP.

## 9. Тестирование DRP

- **Полное тестирование:** раз в квартал (симуляция полного отказа).
- **Частичное тестирование:** раз в месяц (восстановление БД из бэкапа).
- **Результаты тестирования** фиксируются и анализируются.

**Особенности для E‑Commerce:**
- Тестирование должно включать восстановление **заказов и платежей** в согласованном состоянии.
- Проверять восстановление **Event Store** и возможность воспроизведения событий.
