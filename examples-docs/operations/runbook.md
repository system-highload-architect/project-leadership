# Runbook: E‑Commerce Platform

**Версия:** 1.0  
**Дата:** 2026-07-26  
**Статус:** Черновик

---

## 1. Введение

Данный документ содержит **инструкции для операторов и инженеров поддержки** по диагностике и устранению типовых инцидентов в E‑Commerce платформе. Runbook используется в экстренных ситуациях для минимизации времени простоя.

**Цель:** Обеспечить быстрое и предсказуемое реагирование на сбои, восстановление сервиса и эскалацию при необходимости.

---

## 2. Общие принципы

1. **Безопасность прежде всего** — не выполняйте опасных команд (например, `DROP TABLE`) без необходимости.
2. **Логируйте всё** — фиксируйте свои действия, время, причины и результаты.
3. **Не паникуйте** — следуйте инструкциям, не принимайте необдуманных решений.
4. **Эскалируйте своевременно** — если не уверены, что делаете, или не можете восстановить сервис за 15 минут — зовите Tech Lead / DevOps.
5. **Сохраняйте данные для постмортема** — логи, дампы, дашборды — всё пригодится для анализа.

## 3. Инциденты и сценарии

### 3.1 Сервис недоступен (HTTP 5xx / таймауты)

#### Симптомы
- Ошибки 500, 502, 503, 504.
- Таймауты при вызовах API.
- UI не загружается или выдаёт ошибки.
- Пользователи не могут оформить заказ или просмотреть каталог.

#### Возможные причины
1. Сбой в одном из pod'ов (crash loop).
2. Перегрузка БД / Kafka / Redis.
3. Проблемы сети / DNS.
4. Утечка памяти или ресурсов.

#### Действия
1. **Проверьте статус pod'ов:**
   ```bash
   kubectl get pods -n ecommerce
   kubectl describe pod <pod-name> -n ecommerce
   kubectl logs <pod-name> -n ecommerce --tail=100
   ```

2. **Проверьте здоровье API:**
   ```bash
   curl http://api.ecommerce.local/health
   ```

3. **Проверьте ресурсы (CPU, память):**
   ```bash
   kubectl top pods -n ecommerce
   ```

4. **Если pod в статусе `CrashLoopBackOff`:**
   - Посмотрите логи (`kubectl logs`).
   - Проверьте, нет ли ошибок подключения к БД / Kafka / Redis.
   - Перезапустите pod: `kubectl delete pod <pod-name> -n ecommerce`.

5. **Если проблема с БД (Write/Read/Event Store):**
   - Проверьте доступность БД (`kubectl exec` внутрь pod'а и выполните `psql`).
   - Проверьте количество соединений:
     ```sql
     SELECT count(*) FROM pg_stat_activity;
     ```
   - Проверьте блокировки:
     ```sql
     SELECT * FROM pg_locks WHERE NOT granted;
     ```

6. **Если проблема с Kafka:**
   - Проверьте, что брокеры доступны.
   - Проверьте топики и группы потребителей.
   - Проверьте, нет ли накопления сообщений (lag).

7. **Проверьте Redis:**
   ```bash
   redis-cli ping
   redis-cli info memory
   ```

#### Эскалация
Если не удалось восстановить за 15 минут — позвать Tech Lead / DevOps.

### 3.2 Проблемы с платежами (платёжный шлюз недоступен или ошибки)

#### Симптомы
- Платежи не проходят (статус FAILED).
- Пользователи не могут оплатить заказ.
- В логах ошибки `payment gateway timeout` или `payment gateway 5xx`.

#### Возможные причины
1. Платёжный шлюз недоступен.
2. Истёк API-ключ или токен.
3. Превышены лимиты запросов.
4. Некорректные данные карты / СБП.

#### Действия
1. **Проверьте статус платёжного шлюза:**
   ```bash
   curl -I https://payment-gateway.example.com/health
   ```

2. **Проверьте логи Ambassador (если используется):**
   ```bash
   kubectl logs -l app=ambassador -n ecommerce --tail=100 | grep payment
   ```

3. **Проверьте таймауты и Circuit Breaker:**
   - Если CB в Open, проверьте метрики в Grafana.
   - Если CB в Open — подождите таймаут (10–30 секунд) или перезапустите Ambassador.

4. **Проверьте ключи и токены:**
   - Убедитесь, что API-ключи не истекли.
   - Обновите секреты в Vault / Kubernetes Secrets.

5. **Временно отключите платёжный шлюз (only if necessary):**
   - Включите режим «тестового платежа» (mock), если это допустимо для бизнеса.

#### Эскалация
Вызвать разработчика, ответственного за платёжную интеграцию, или DevOps.

### 3.3 Задержки в обработке событий (Kafka lag)

#### Симптомы
- Статусы заказов не обновляются (NEW → PAID → SHIPPED).
- Уведомления не отправляются.
- Проекции (CQRS read models) устаревают.

#### Возможные причины
1. Потребители Kafka отстают (lag растёт).
2. Один из потребителей упал или завис.
3. Партиций недостаточно для текущей нагрузки.
4. Проблемы с сетью или брокером.

#### Действия
1. **Проверьте lag потребителей:**
   ```bash
   kafka-consumer-groups --bootstrap-server kafka:9092 --group <group> --describe
   ```
   Обратите внимание на столбец `LAG`.

2. **Если lag растёт:**
   - Увеличьте количество потребителей (replicas) для нужного сервиса.
   - Проверьте, не завис ли один из потребителей (перезапустите pod).

3. **Если lag не уменьшается:**
   - Проверьте, что топик имеет достаточное количество партиций.
   - При необходимости увеличьте число партиций:
     ```bash
     kafka-topics --bootstrap-server kafka:9092 --alter --topic orders --partitions 10
     ```

4. **Проверьте ошибки в логах потребителей:**
   ```bash
   kubectl logs -l app=order-consumer -n ecommerce --tail=100 | grep -i error
   ```

#### Эскалация
Вызвать DevOps или администратора Kafka.

### 3.4 Сбои в проекциях (CQRS read models)

#### Симптомы
- Запросы к read-моделям возвращают устаревшие данные.
- Данные отсутствуют (пустые списки заказов, товаров).
- Ошибки при запросах (500 или таймауты).

#### Возможные причины
1. Проекционный сервис упал или завис.
2. Задержка в обработке событий (связано с п. 3.3).
3. Ошибки в логике проекции (например, неправильная агрегация).
4. Read DB перегружена или недоступна.

#### Действия
1. **Проверьте статус проекционного сервиса:**
   ```bash
   kubectl get pods -l app=projection -n ecommerce
   kubectl logs -l app=projection -n ecommerce --tail=100
   ```

2. **Проверьте отставание проекций (если есть метрики):**
   - В Grafana посмотрите дашборд `Projection Lag`.
   - Если lag > 10 минут — проверьте Kafka потребителей.

3. **Проверьте Read DB:**
   ```bash
   kubectl exec -it postgres-read-0 -n ecommerce -- psql -U ecommerce_user -d ecommerce_read_db -c "SELECT count(*) FROM orders_read;"
   ```

4. **Перезапустите проекционный сервис:**
   ```bash
   kubectl delete pod -l app=projection -n ecommerce
   ```

#### Эскалация
Вызвать разработчика, ответственного за CQRS/Event Sourcing.

### 3.5 Проблемы с Event Sourcing (восстановление агрегатов)

#### Симптомы
- Заказы не загружаются (ошибка 404 или 500).
- Агрегаты не восстанавливаются (неправильное состояние).
- В логах ошибки `failed to replay events` или `event stream corrupted`.

#### Возможные причины
1. Повреждённые события в Event Store (например, некорректный JSON).
2. Изменение структуры событий без версионирования.
3. Event Store недоступен или перегружен.

#### Действия
1. **Проверьте Event Store:**
   ```sql
   SELECT * FROM order_events WHERE aggregate_id = '<order_id>' ORDER BY created_at;
   ```

2. **Проверьте событие, вызвавшее ошибку:**
   - Посмотрите `event_data` — возможно, там некорректный JSON.
   - Если событие повреждено, исправьте вручную (с осторожностью!) или пропустите.

3. **Проверьте версионирование:**
   - Убедитесь, что агрегат поддерживает текущую версию события.
   - Если событие устарело, напишите миграцию для обновления данных.

4. **Перезапустите сервис, который восстанавливает агрегаты:**
   ```bash
   kubectl delete pod -l app=order-service -n ecommerce
   ```

#### Эскалация
Вызвать разработчика, ответственного за Event Sourcing и архитектуру.

### 3.6 Ошибки в Saga (распределённые транзакции)

#### Симптомы
- Заказ застрял в статусе `NEW` (не переходит в `PAID` или `CANCELLED`).
- Компенсация не сработала (заказ отменён, но платёж не возвращён).
- В логах ошибки `Saga step failed`.

#### Возможные причины
1. Один из шагов Saga (платёж, резервирование, уведомление) завершился ошибкой.
2. Оркестратор не получил ответа от сервиса (таймаут).
3. Saga Coordinator потерял состояние (сбой и перезапуск без восстановления).

#### Действия
1. **Проверьте состояние Saga:**
   ```sql
   SELECT * FROM saga_state WHERE id = '<saga_id>';
   ```
   Посмотрите `status` и `step_results`.

2. **Найдите ошибку в шагах:**
   - Проверьте логи сервисов, участвующих в Saga (Payment, Inventory, Notification).
   - Если ошибка временная (таймаут), попробуйте повторить шаг вручную (если есть API для повторного запуска).

3. **Если Saga застряла в `IN_PROGRESS`:**
   - Если это допустимо, перезапустите оркестратор:
     ```bash
     kubectl delete pod -l app=saga-orchestrator -n ecommerce
     ```
   - Если нет — выполните компенсацию вручную (отмена заказа, возврат платежа).

4. **Проверьте, что компенсация отработала:**
   - Проверьте статус платежа (должен быть REFUNDED).
   - Проверьте статус заказа (должен быть CANCELLED).

#### Эскалация
Вызвать разработчика, ответственного за Saga и бизнес-логику.

### 3.7 Проблемы с базой данных (соединение потеряно, нарушения целостности)

#### Симптомы
- В логах `connection refused`, `too many connections`, `deadlock detected`.
- Операции зависают или падают.

#### Возможные причины
1. БД недоступна (сбой реплики, перезагрузка).
2. Исчерпаны соединения (max_connections).
3. Deadlock (взаимная блокировка транзакций).
4. Диск заполнен.

#### Действия
1. **Проверьте доступность БД:**
   ```bash
   kubectl exec -it <backend-pod> -n ecommerce -- psql -h postgres-write-service -U ecommerce_user -d ecommerce_db -c "SELECT 1"
   ```

2. **Проверьте количество соединений:**
   ```sql
   SELECT count(*) FROM pg_stat_activity;
   SELECT count(*) FROM pg_stat_activity WHERE state = 'idle';
   ```

3. **Завершите висячие соединения (если нужно):**
   ```sql
   SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND pid <> pg_backend_pid();
   ```

4. **Проверьте дисковое пространство:**
   ```bash
   df -h /var/lib/postgresql/data
   ```

5. **Проверьте наличие deadlock'ов:**
   ```sql
   SELECT * FROM pg_locks WHERE NOT granted;
   ```

#### Эскалация
Если не удаётся восстановить — вызвать DBA или DevOps.

## 5. Постмортем (Post-Mortem)

После каждого инцидента проводится анализ:

1. **Что произошло?** — краткое описание инцидента.
2. **Когда произошло?** — время начала и окончания.
3. **Причина** — корневая причина (root cause).
4. **Действия** — что делали для восстановления.
5. **Уроки** — что можно улучшить (мониторинг, документация, код, инфраструктура).
6. **Action items** — конкретные задачи для предотвращения повторения.
