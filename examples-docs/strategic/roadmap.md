---

## 1. Введение

Дорожная карта определяет **этапы развития** E‑Commerce платформы, ключевые вехи и сроки. Она служит инструментом синхронизации команды, менеджеров и стейкхолдеров относительно того, **что и когда** будет реализовано.

Карта построена по принципу **эволюционной архитектуры**:
- Начинаем с **модульного монолита** для быстрого запуска MVP.
- Постепенно вводим паттерны (Saga, CQRS, Sidecar, Ambassador, Circuit Breaker) по мере роста нагрузки и сложности.
- Переходим к **микросервисам** только когда это становится экономически и технически обоснованным.

Все этапы соответствуют стратегическим целям, описанным в [product-vision.md](product-vision.md).

## 2. Этапы развития

### 🚀 Этап 1: Фундамент (MVP) — Q3 2026 (3 месяца)
**Цель:** Быстро запустить работающий прототип с базовым функционалом.

| Веха | Описание | Срок |
|------|----------|------|
| **Архитектура** | Утверждены ADR, диаграммы C4/ER/UML, модель данных | Неделя 1–2 |
| **Настройка инфраструктуры** | Репозиторий, CI/CD, PostgreSQL, Kafka (dev) | Неделя 2–3 |
| **Базовые сущности** | Реализованы модели Product, Order, Payment, User, Notification | Неделя 3–4 |
| **REST API (MVP)** | CRUD для товаров, заказов, платежей, пользователей | Неделя 4–6 |
| **Базовое событийное ядро** | Публикация событий при изменениях (Kafka) | Неделя 6–7 |
| **Интерфейс оператора** | Web UI (React) для управления товарами и заказами | Неделя 7–9 |
| **Интеграция с платёжным шлюзом** | Поддержка банковских карт и СБП | Неделя 9–10 |
| **Документация** | API-контракты (OpenAPI), первые ADR, README | Неделя 10–12 |
| **Пилот с внутренним пользователем** | Тестирование на реальных сценариях, сбор обратной связи | Неделя 10–12 |

**Результат этапа:** Рабочий MVP, который можно показать первым клиентам.

**Используемые паттерны:**
- Модульный монолит
- Базовая EDA (Kafka для событий)
- Clean Architecture внутри модулей

---

### 🔧 Этап 2: Надёжность и масштабирование — Q4 2026 (3 месяца)
**Цель:** Улучшить производительность, надёжность и добавить ключевые паттерны.

| Веха | Описание | Срок |
|------|----------|------|
| **Circuit Breaker & Retry** | Защита от сбоев платёжного шлюза и внешних API | Неделя 1–2 |
| **Saga Orchestration** | Распределённые транзакции для сложных заказов (платёж + резервирование + уведомление) | Неделя 2–4 |
| **CQRS (базовый)** | Разделение моделей для чтения (проекции) и записи | Неделя 4–6 |
| **Sidecar для логирования и метрик** | Вынос сквозной функциональности в sidecar-контейнер | Неделя 6–7 |
| **Мониторинг и логирование** | Настройка Prometheus, Grafana, ELK/Loki | Неделя 7–8 |
| **SLO/SLI** | Определены метрики, настроены алерты | Неделя 8–9 |
| **Оптимизация БД** | Индексы, кэширование (Redis), подготовка к шардированию | Неделя 9–10 |
| **API Gateway** | Единая точка входа, авторизация, rate limiting | Неделя 10–12 |
| **Тренинг команды** | Онбординг, технические сессии, документация | Неделя 10–12 |

**Результат этапа:** Система готова к эксплуатации с гарантированной надёжностью 99.9%.

**Используемые паттерны:**
- Circuit Breaker (для внешних вызовов)
- Saga (Orchestration)
- CQRS (базовый)
- Sidecar (для логирования, метрик, трассировки)
- Ambassador (для внешних API — платёжный шлюз, нотификации)

---

### 🌍 Этап 3: Интеграции и гибкость — Q1 2027 (3 месяца)
**Цель:** Подключение внешних систем, расширение API, подготовка к микросервисам.

| Веха | Описание | Срок |
|------|----------|------|
| **Расширение событийной модели** | Новые события, проекции для аналитики | Неделя 1–3 |
| **Event Sourcing для Order Service** | Хранение событий заказов как источника истины | Неделя 3–5 |
| **CQRS (полноценный)** | Отдельные read-модели для аналитики и поиска | Неделя 5–7 |
| **Strangler Pattern** | Вынос модулей (Payment, Notification) в отдельные микросервисы | Неделя 7–9 |
| **Service Mesh (базовый)** | Управление трафиком, безопасность, наблюдаемость | Неделя 9–11 |
| **Пилот с внешними клиентами** | Подключение 5 клиентов в боевом режиме | Неделя 11–12 |

**Результат этапа:** Система масштабируется до 1000+ заказов в день, готова к промышленной эксплуатации.

**Используемые паттерны:**
- Event Sourcing (для Order Service)
- CQRS (полноценный)
- Strangler Pattern (для миграции к микросервисам)
- Service Mesh (Istio/Linkerd)
- Ambassador (для внешних интеграций)

## 5. Риски и смягчения

| Риск | Этап | Меры |
|------|------|------|
| Задержка интеграции с платёжным шлюзом | Этап 1 | Ранний доступ к тестовому API, моки |
