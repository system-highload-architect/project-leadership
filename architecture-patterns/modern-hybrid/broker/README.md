# Broker Architecture

**Broker Architecture** — это архитектурный стиль, при котором все коммуникации между сервисами проходят через центральный брокер сообщений (например, Kafka, RabbitMQ, NATS). Сервисы не общаются напрямую, а публикуют и подписываются на сообщения через брокер.

Это обеспечивает слабую связанность, асинхронность и масштабируемость.

---

## 🧠 Основные принципы

1. **Централизованный брокер.**  
   Все сообщения проходят через брокер, который управляет очередями, топиками, партициями.

2. **Публикация/подписка.**  
   Сервисы публикуют сообщения в топики, другие сервисы подписываются на них.

3. **Слабая связанность.**  
   Сервисы не знают друг о друге — только о брокере.

4. **Асинхронность.**  
   Публикация и обработка происходят асинхронно, что повышает отказоустойчивость.

---

## 🧩 Когда использовать Broker Architecture

- Нужна асинхронная коммуникация между сервисами.
- Много потребителей и поставщиков сообщений.
- Важна слабая связанность и масштабируемость.
- Требуется долговременное хранение событий (replay).

---

## 🏗️ Архитектура

```
[ Service A ] → [ Publisher ] → [ Broker (Kafka) ] → [ Consumer ] → [ Service B ]
                                    │
                                    ├── [ Consumer ] → [ Service C ]
                                    └── [ Consumer ] → [ Service D ]
```

---

## 🔧 Инструменты

- **Apache Kafka** — высокопроизводительный, распределённый, с долговременным хранением.
- **RabbitMQ** — надёжный, с поддержкой сложной маршрутизации.
- **NATS** — лёгкий, быстрый, для микросервисов.
- **AWS SQS/SNS** — управляемый брокер в облаке.

---

## ⚖️ Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| ✅ Слабая связанность | ❌ Единая точка отказа (брокер) |
| ✅ Асинхронность и отказоустойчивость | ❌ Сложность отладки и мониторинга |
| ✅ Масштабируемость | ❌ Задержка (асинхронность) |
| ✅ Долговременное хранение (replay) | ❌ Требует управления топиками и партициями |
