# Service Mesh

**Service Mesh** — это инфраструктурный слой, который управляет коммуникацией между сервисами в распределённой системе. Он обеспечивает наблюдаемость, безопасность, маршрутизацию и отказоустойчивость без изменения кода сервисов.

Service Mesh обычно реализуется с помощью **sidecar-прокси** (например, Envoy), которые перехватывают весь сетевой трафик между сервисами.

---

## 🧠 Основные принципы

1. **Прозрачность для приложений.**  
   Сервисы не знают о Service Mesh — они просто отправляют запросы, а mesh управляет трафиком.

2. **Безопасность.**  
   Взаимная TLS (mTLS) между сервисами, авторизация на уровне сети.

3. **Наблюдаемость.**  
   Метрики, логи, трассировка собираются автоматически.

4. **Управление трафиком.**  
   Маршрутизация, канареечные релизы, A/B-тестирование, отказоустойчивость (retry, timeout, circuit breaker).

---

## 🧩 Когда использовать Service Mesh

- У вас десятки или сотни микросервисов.
- Нужен единый подход к безопасности (mTLS) и наблюдаемости.
- Команды не хотят заботиться о сетевых вопросах в коде.
- Требуется сложная маршрутизация (canary, blue-green, A/B).

---

## 🏗️ Архитектура

```
[ Service A ] ↔ [ Sidecar (Envoy) ] ↔ [ Service Mesh Control Plane ] ↔ [ Sidecar (Envoy) ] ↔ [ Service B ]
```

---

## 🔧 Инструменты

- **Istio** — самый популярный, мощный, но сложный.
- **Linkerd** — лёгкий, быстрый, простой в установке.
- **Consul** — от HashiCorp, интеграция с их экосистемой.
- **Kuma** — на основе Envoy, поддерживает multi-cluster.

---

## ⚖️ Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| ✅ Безопасность (mTLS) | ❌ Сложность настройки и эксплуатации |
| ✅ Наблюдаемость (метрики, трассировка, логи) | ❌ Дополнительная задержка (latency) |
| ✅ Управление трафиком (canary, retry, circuit breaker) | ❌ Ресурсоёмкость (каждый Pod имеет sidecar) |
| ✅ Единый подход для всех сервисов | ❌ Требует обучения команды |
