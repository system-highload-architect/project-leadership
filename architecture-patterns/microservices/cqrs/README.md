# Микросервисы с CQRS

**CQRS (Command Query Responsibility Segregation)** — это паттерн, разделяющий модели для **чтения** (Query) и **записи** (Command). Вместо использования одной модели данных для всех операций, CQRS предлагает использовать отдельные модели для обновления состояния и для получения данных.

Это позволяет оптимизировать каждую сторону независимо (например, использовать разные БД для чтения и записи), упрощает масштабирование и улучшает производительность.

---

## 🧠 Основные принципы

1. **Команды (Commands)** — изменяют состояние системы (CREATE, UPDATE, DELETE). Не возвращают данные (или возвращают только идентификатор/статус).
2. **Запросы (Queries)** — получают данные, не изменяют состояние.
3. **Модель записи** — оптимизирована для вставки/обновления (нормализованная, транзакционная).
4. **Модель чтения** — оптимизирована для выборки (денормализованная, кэшированная, с индексами).
5. **Синхронизация** — между моделями часто асинхронная (через события), что даёт **eventual consistency** (согласованность в конечном счёте).

---

## 🧩 Когда использовать CQRS

1. **Нагрузка на чтение и запись сильно различается** (читают много, пишут редко, или наоборот).
2. **Требуются разные модели для чтения и записи** (например, чтение — через Elasticsearch, запись — через PostgreSQL).
3. **Сложная бизнес-логика** требует отделения команд от запросов для упрощения.
4. **Event Sourcing** уже используется — CQRS идеально сочетается с ним.
5. **Нужна высокая производительность и масштабируемость** для read-интенсивных сценариев.

---

## 🏗️ Архитектура CQRS

```
[ Клиент ]
    │
    ├── Command → [ Command Handler ] → [ Write DB (Event Store) ]
    │
    └── Query  → [ Query Handler ]  → [ Read DB (Projection) ]
                                              ▲
                                              │
                                    [ Projection Service ] ← события из Write DB
```

---

## 🔧 Реализация

**Команды и запросы на Go:**

```go
// Command
type CreateOrderCommand struct {
    CustomerID string
    Items      []OrderItem
}

// Command Handler
func (h *OrderCommandHandler) HandleCreateOrder(ctx context.Context, cmd CreateOrderCommand) error {
    // бизнес-логика, сохранение в Write DB
}

// Query
type GetOrderQuery struct {
    OrderID string
}

// Query Handler
func (h *OrderQueryHandler) HandleGetOrder(ctx context.Context, query GetOrderQuery) (*OrderDTO, error) {
    // чтение из Read DB (оптимизированная модель)
}
```

---

## ⚖️ Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| ✅ Оптимизация каждой стороны (чтение/запись) | ❌ Увеличение сложности |
| ✅ Упрощение моделей | ❌ Синхронизация между моделями (eventual consistency) |
| ✅ Независимое масштабирование | ❌ Дополнительная инфраструктура |
| ✅ Естественная интеграция с Event Sourcing | ❌ Сложность понимания для команды |
