# Базовая событийно-ориентированная архитектура (EDA)

**Базовая EDA** — это архитектурный стиль, при котором компоненты системы общаются друг с другом через **асинхронные события**. Вместо прямых синхронных вызовов (REST, gRPC) сервисы публикуют события о том, что произошло, и реагируют на события, которые им интересны.

EDA — это **не просто «использование брокера сообщений»**. Это целая парадигма мышления, которая требует переосмысления того, как данные и команды движутся в системе.

---

## 🧠 Основные принципы

1. **Событие (Event)** — факт, который произошёл в системе (например, «заказ создан»). Событие неизменяемо и содержит информацию о том, что случилось.

2. **Брокер событий (Event Broker)** — промежуточное звено (Kafka, RabbitMQ, NATS), которое принимает события и доставляет их подписчикам.

3. **Подписчики (Subscribers)** — компоненты, которые реагируют на определённые события и выполняют свои действия.

4. **Асинхронность** — публикация и обработка событий не блокируют друг друга.

5. **Слабая связанность** — сервисы не знают друг о друге, только о брокере и событиях.

---

## 🧩 Когда использовать базовую EDA

- Нужна слабая связанность между компонентами.
- Есть асинхронные процессы (ответ на запрос не нужен немедленно).
- Система растёт — добавление новых подписчиков не должно требовать изменений в существующем коде.
- Есть несколько потребителей одного события (например, уведомления, аналитика, логирование).
- Требуется масштабирование и отказоустойчивость.

---

## 🏗️ Архитектура

```
[ Service A ] → [ Event ] → [ Broker ] → [ Event ] → [ Service B ]
                                    │
                                    ├── [ Event ] → [ Service C ]
                                    └── [ Event ] → [ Service D ]
```

## 🔧 Реализация на Go (пример с Kafka)

**Публикация события:**

```go
func (s *OrderService) CreateOrder(order Order) error {
    // сохраняем заказ в БД
    s.repo.Save(order)

    // создаём событие
    event := OrderCreated{
        OrderID:    order.ID,
        CustomerID: order.CustomerID,
        Timestamp:  time.Now(),
    }

    // публикуем в Kafka
    return s.kafka.Publish("orders", event)
}
```

**Подписка на событие:**

```go
func (s *PaymentService) StartConsumer() error {
    return s.kafka.Consume("orders", func(msg []byte) error {
        var event OrderCreated
        json.Unmarshal(msg, &event)

        // обрабатываем событие (например, списываем средства)
        return s.processPayment(event.OrderID)
    })
}
```

## ⚖️ Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| ✅ Слабая связанность компонентов | ❌ Сложность отладки и трассировки |
| ✅ Асинхронность и отказоустойчивость | ❌ Eventual consistency (согласованность в конечном счёте) |
| ✅ Лёгкость добавления новых подписчиков | ❌ Нужно обеспечить идемпотентность |
| ✅ Естественное отражение предметной области | ❌ Сложнее проектировать бизнес-процессы |

---

## 🚀 Использование в реальном проекте

1. **Определите события** — какие события публикуются и на какие подписываются сервисы.
2. **Выберите брокер** — Kafka (для больших объёмов, replay), RabbitMQ (для сложной маршрутизации), NATS (для лёгкости).
3. **Реализуйте публикацию и подписку** через единый интерфейс (пакет `events`).
4. **Обеспечьте идемпотентность** — каждое событие может быть доставлено несколько раз.
5. **Внедрите мониторинг** — отслеживайте задержки, ошибки, размер очередей.
