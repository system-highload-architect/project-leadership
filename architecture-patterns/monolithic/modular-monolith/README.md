# Модульный монолит

**Модульный монолит** — это архитектурный стиль, при котором приложение разрабатывается как единое развёртываемое целое (монолит), но внутри оно чётко разделено на слабо связанные модули, каждый из которых соответствует отдельной бизнес-способности (Bounded Context в терминах DDD).

Этот подход сочетает в себе **простоту монолита** (единый деплой, транзакции, простота отладки) и **готовность к выделению** модулей в отдельные микросервисы при необходимости.

---

## 🧠 Основные принципы

1. **Чёткие границы между модулями.**  
   Каждый модуль соответствует одному Bounded Context. Модули общаются через чётко определённые интерфейсы (API, события).

2. **Единая кодовая база и единый деплой.**  
   Все модули собираются в один бинарный файл или Docker-образ.

3. **Слабая связанность.**  
   Модули не должны знать о внутренней реализации друг друга. Общение через интерфейсы и события.

4. **Готовность к распилу.**  
   Модули проектируются так, чтобы их можно было легко вынести в отдельные сервисы без изменения кода (с помощью паттерна Strangler).

---

## 🧩 Когда использовать модульный монолит

- Команда небольшая (до 10–15 разработчиков).
- Требования нестабильны или только формируются.
- Нужен быстрый выход на рынок (MVP).
- Хочется сохранить возможность перехода к микросервисам в будущем.
- Нет жёстких требований к независимому масштабированию частей системы.

---

## 🏗️ Архитектура

```
[ Модуль A ] ←→ [ Модуль B ] ←→ [ Модуль C ]
     │                │                │
     └────────────────┼────────────────┘
                      ▼
              [ Единая БД (с разделением схем) ]
```

Модули общаются синхронно (через внутренние вызовы) и асинхронно (через внутреннюю шину событий, которая может быть заменена на Kafka).

## ⚖️ Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| ✅ Быстрый старт и простота деплоя | ❌ Единая точка отказа (ошибка в одном модуле может уронить всё) |
| ✅ Чёткие границы, поддерживаемость | ❌ Ограниченное масштабирование (нельзя масштабировать отдельные модули) |
| ✅ Готовность к выделению в микросервисы | ❌ Может «разрастись» в «большой ком грязи», если не соблюдать границы |
| ✅ Единые транзакции (ACID) | ❌ Все модули на одном языке/стеке |

---

## 🔄 Переход к микросервисам

Модульный монолит идеально подходит для эволюционного перехода к микросервисам:

1. Выделяйте модули с чёткими границами.
2. Замените внутреннюю шину на Kafka (без изменения кода модулей).
3. Постепенно выносите модули в отдельные сервисы, используя Strangler Pattern.
