# Микрокернел (плагинная архитектура)

**Микрокернел** (или плагинная архитектура) — это архитектурный стиль, при котором система состоит из **минимального ядра**, обеспечивающего базовую функциональность, и **подключаемых модулей (плагинов)**, которые расширяют эту функциональность. Модули могут быть добавлены, удалены или заменены без изменения ядра.

Этот подход особенно полезен для систем с широкими возможностями кастомизации, где разные клиенты или пользователи могут нуждаться в разных наборах функций.

---

## 🧠 Основные принципы

1. **Ядро (Core).**  
   Содержит минимальную функциональность, необходимую для работы системы: загрузку модулей, управление жизненным циклом, базовые API, безопасность.

2. **Плагины (Plugins).**  
   Реализуют конкретную функциональность (например, платёжные методы, способы доставки, форматы отчётов). Подключаются к ядру через чётко определённые интерфейсы (контракты).

3. **Контракты (Contracts).**  
   Интерфейсы, которые определяют, как плагины взаимодействуют с ядром и друг с другом.

4. **Динамическая загрузка.**  
   Плагины могут загружаться и выгружаться во время выполнения (горячая замена).

---

## 🧩 Когда использовать микрокернел

- Приложение должно поддерживать расширяемость (плагины, дополнения, сторонние интеграции).
- Разные клиенты или сценарии использования требуют разных наборов функций.
- Функциональность меняется часто, и обновления должны быть изолированы.
- Требуется возможность подключать сторонние модули без изменения ядра.

**Примеры:** IDE (VS Code, IntelliJ), браузеры (Chrome, Firefox), CMS (WordPress, Drupal), системы управления контентом.

---

## 🏗️ Архитектура

```
[ Клиент ]
    │
    ▼
[ Ядро (Core) ] ← загрузка плагинов, управление, базовые API
    │
    ├── [ Плагин A ]
    ├── [ Плагин B ]
    └── [ Плагин C ]
```

Каждый плагин реализует один или несколько интерфейсов, определённых ядром.

---

## 🔧 Реализация на Go (пример)

**Интерфейс плагина:**

```go
type Plugin interface {
    Name() string
    Init(config map[string]interface{}) error
    Execute(ctx context.Context, args map[string]interface{}) (interface{}, error)
}
```

**Ядро (загрузка плагинов):**

```go
func LoadPlugins(pluginDir string) ([]Plugin, error) {
    var plugins []Plugin
    files, _ := os.ReadDir(pluginDir)
    for _, file := range files {
        if strings.HasSuffix(file.Name(), ".so") {
            p, err := plugin.Open(filepath.Join(pluginDir, file.Name()))
            if err != nil {
                continue
            }
            sym, err := p.Lookup("NewPlugin")
            if err != nil {
                continue
            }
            newPlugin, ok := sym.(func() Plugin)
            if !ok {
                continue
            }
            plugins = append(plugins, newPlugin())
        }
    }
    return plugins, nil
}
```

## ⚖️ Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| ✅ Расширяемость (добавление новых плагинов без изменения ядра) | ❌ Усложнение архитектуры (управление плагинами, контракты) |
| ✅ Изоляция изменений (ошибка в плагине не роняет ядро) | ❌ Сложность версионирования (совместимость плагинов с ядром) |
| ✅ Возможность кастомизации под разных клиентов | ❌ Дополнительные накладные расходы (загрузка, коммуникация) |
| ✅ Горячая замена (без перезапуска) | ❌ Менее производителен, чем монолит (если много плагинов) |

---

## 🚀 Использование в реальном проекте

1. **Определите контракты** — интерфейсы, которые должны реализовывать плагины.
2. **Реализуйте ядро** — загрузка плагинов, управление жизненным циклом, базовые API.
3. **Разработайте плагины** — как отдельные модули (или отдельные репозитории).
4. **Обеспечьте безопасность** — плагины должны выполняться в изолированной среде (sandbox) при необходимости.
